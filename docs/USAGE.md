## Что нужно знать сразу

- SDK — клиент пользовательского API ИТД, а не официальный Bot API. Бот действует от имени своего аккаунта.
- Для отправки сообщений аккаунту бота нужна подписка **«ИТД НУКСТА»**. Без неё сервер возвращает `nuksta_required`, см. [коды ошибок](#коды-ошибок-сервера). Это не подписка пользователя на аккаунт бота, которую проверяет `ctx.is_subscribed()`.
- Методы возвращают обычные словари и списки JSON с исходными именами полей. Исключение — профили (`User`).
- Адрес по умолчанию: `https://xn--d1ah4a.com`. Другой задаётся через `Bot(token, base_url="https://...")`.
- Каждый запрос идёт через [защиту от лимитов](RATE_LIMITS.md), поэтому бот иногда немного ждёт. Это нормально.

## Команды и обработчики

```python
from itd_bot import Dispatcher

router = Dispatcher.from_bot(bot)

@router.command("start")
def start(ctx):
    ctx.reply("Привет! Напишите /help")

@router.command("echo")
def echo(ctx):
    ctx.reply(ctx.args or "Добавьте текст после команды")

@router.message()
def any_message(ctx):
    print(ctx.sender_id, ctx.chat_id, ctx.text)

@router.photo()
def on_photo(ctx):
    for photo in ctx.photo:
        print(photo.filename, photo.mime, photo.size)

router.run_polling(state_path=".bot-state.json")
```

`Dispatcher.from_bot(bot)` сам узнаёт ID бота, чтобы он не отвечал самому себе.

**Какой обработчик сработает.** Сначала команды, потом `photo()` (для сообщений с фото), потом `message()` для всего остального. Суффикс `@username` в команде учитывается, только если совпадает с именем бота.

**Что есть в контексте `ctx`:**

| Что | Зачем |
|---|---|
| `ctx.text`, `ctx.args`, `ctx.chat_id`, `ctx.sender_id` | Текст, аргументы команды, чат и отправитель |
| `ctx.attachments`, `ctx.photo` | Все вложения и только картинки (`attachment.download(path)` скачивает файл) |
| `ctx.reply(...)` | Ответить; возвращает словарь |
| `ctx.reply_message(...)` | Ответить и получить объект с `edit()` и `delete()` |
| `ctx.reply_photo / reply_video / reply_music / reply_file` | Ответить файлом |
| `ctx.react`, `ctx.remove_reaction`, `ctx.delete_message`, `ctx.forward_to` | Действия с сообщением |
| `ctx.get_sender()` | Профиль отправителя |
| `ctx.is_subscribed()` | `True`, `False` или `None`, если сервер не сказал |
| `ctx.message`, `ctx.event` | Исходные словари |

Для реакций, правок и удалений есть `@router.reaction()`, `@router.edited()` и `@router.deleted()`. В контексте у них `chat_id`, `message_id`, `reactions` и `event`; при массовом удалении ID лежат в `ctx.event["message_ids"]`.

> **Хорошо знать.** Команды живут только внутри SDK, на сервере ИТД они нигде не регистрируются. Старые `@router.on_message` (с аргументами `(event, message)`) и `on_event` тоже работают, но `on_message` нельзя использовать вместе с `message()`. `on_message` выдаёт `DeprecationWarning`, замена ему `message()`; в 1.x метод не удаляется. Общая [политика совместимости и устаревания](../README.md#статус-и-гарантии) описана в README.

Готовый пример: [`examples/commands.py`](../examples/commands.py).

### Прочтение сообщений

Перед вызовом обработчика бот отмечает входящее сообщение прочитанным, и если отметка не удалась, обработчик не запускается. Это поведение можно изменить:

```python
Dispatcher(bot, self_user_id="...", read_mode="background")  # не ждать ответа сервера
Dispatcher(bot, self_user_id="...", read_mode="off")         # не отмечать вовсе
```

В режиме `background` ошибка отметки только попадёт в лог, а обработчик всё равно выполнится.

## Сообщения

```python
bot.send_message("CHAT_ID", "Привет!")
bot.send_message("CHAT_ID", "Ответ", reply_to_id="MESSAGE_ID")
bot.send_message_to_user("USER_ID", "Привет, личное сообщение")

bot.edit_message("CHAT_ID", "MESSAGE_ID", "Новый текст")
bot.delete_messages("CHAT_ID", ["MESSAGE_ID"], for_everyone=False)
bot.forward_messages("CHAT_ID", "SOURCE_CHAT_ID", ["MESSAGE_ID"])
```

Историю читают `get_messages` и `get_messages_around`, список чатов — `get_chats`. Полный перечень методов — в [справочнике](API_REFERENCE.md).

Для пересылки можно передать свои клиентские ID:

```python
bot.forward_messages(
    "CHAT_ID",
    "SOURCE_CHAT_ID",
    ["MESSAGE_ID"],
    client_message_ids={"MESSAGE_ID": "CLIENT_MESSAGE_ID"},
)
```

`client_message_ids` принимает словарь `{исходный message_id: клиентский ID}` или прежний список `list[str]`. Список с такой же длиной, как `message_ids`, преобразуется в словарь по порядку: первый клиентский ID соответствует первому сообщению. Готовый словарь передаётся без преобразования. `None`, пустой список и пустой словарь не включаются в запрос; поле остаётся необязательным.

Число элементов непустого списка должно совпадать с числом сообщений. При разной длине SDK сохраняет прежний запрос для серверной проверки, без нового локального исключения.

Форма объекта подтверждена клиентским бандлом (`index-1f7c8b01465d.js`, `Object.fromEntries` при пересылке). При проверке 26 ноября 2026 года в разрешённом тестовом чате сервер принял объект (HTTP 201) и отклонил исходный список (HTTP 400). Вызовы SDK со словарём и с преобразованным списком оба завершились HTTP 201. SDK выбирает формат до отправки, без попытки повторить запись в другом формате. Клиентские ID не считаются гарантией от дублей, см. [#19](https://github.com/itd-social/CHATBOT-SDK/issues/19).

> **Хорошо знать.** Если запрос на отправку оборвался по сети, SDK его не повторяет: сообщение могло уйти, а могло и нет. Что делать дальше, решает ваш бот. Как сервер обрабатывает `client_message_id`, мы не знаем, так что гарантией от дублей это считать нельзя.

### Лимиты текста и вложений

| Ограничение | Где применяется |
|---|---|
| Текст до 4096 символов | Интерфейс сайта |
| До 50 сущностей форматирования | Клиент сайта и конструктор `Text` в SDK |
| Отправка стикеров недоступна | Клиент сайта; SDK не предоставляет отдельного метода отправки стикеров |
| Текст до 131072 байт UTF-8 | Серверное ограничение, указанное в исследовании #42 |

Клиентские ограничения относятся к интерфейсу сайта и не обязательно совпадают с серверными. SDK не обрезает текст до 4096 символов и не проверяет предел в байтах; размер UTF-8 можно посчитать как `len(text.encode("utf-8"))`. `Text` проверяет количество сущностей и при превышении 50 выдаёт `ValueError`; при передаче `entities` напрямую эту проверку SDK не делает.

Сведения о сайте и серверном пределе взяты из [#42](https://github.com/itd-social/CHATBOT-SDK/issues/42). Ссылки на бандл из Issue при подготовке этой документации не проверены: бандл недоступен, живые запросы не выполнялись.

## Форматирование текста

`Text` собирает текст со стилями. Markdown и экранирование не нужны, а эмодзи считаются правильно.

```python
from itd_bot import Text

content = (Text("Привет 👋 ")
           .bold("жирный")
           .add(" и ")
           .italic("курсив")
           .add(". ")
           .link("Открыть сайт", "https://example.com"))

bot.send_formatted("CHAT_ID", content)
```

Доступны `bold`, `italic`, `underline`, `strike`, `code`, `spoiler` и `link`. Стили можно сочетать: `Text().add("текст", styles=("bold", "italic"))`. Внутри ответа в обработчике есть `ctx.reply_formatted(content)`.

Для ручной отправки: `text, entities = content.build()`, затем передайте оба значения в `send_message`.

Конструктор ограничивает текст 50 сущностями, см. [лимиты](#лимиты-текста-и-вложений). Формирование текста и сущностей проверено локальными тестами; отображение стилей на живом ИТД не проверялось.

## Файлы

### Отправка

```python
bot.send_file("CHAT_ID", "report.pdf", text="Отчёт")
bot.send_photo("CHAT_ID", "photo.png", caption="Фото")
bot.send_video("CHAT_ID", "video.mp4", caption="Видео")
bot.send_music("CHAT_ID", "track.mp3", caption="Музыка")  # есть и send_audio
```

Подойдёт любой тип файла, который примет сервер. Файл не должен быть пустым и больше 2 ГиБ. Данные уходят частями по 5 МиБ, так что память не страдает. Ход загрузки можно отслеживать через `on_progress(sent, total)`.

Если нужно загрузить файл заранее и отправить позже:

```python
result = bot.upload_file("report.pdf")
bot.send_message("CHAT_ID", "Отчёт", attachments=[result["fileId"]])
```

### Фото, видео и музыка

По умолчанию отправляются исходные байты. Хотите сжать? Установите расширение и добавьте `compress=True`:

```sh
python -m pip install "itd-chatbot-sdk[images]"
```

```python
bot.send_photo("CHAT_ID", "photo.png", caption="Фото", compress=True)
bot.send_video("CHAT_ID", "video.mov", compress=True)
```

- **Фото** превращается в JPEG: длинная сторона до 1920 пикселей, качество 70, прозрачность заменяется белым фоном. GIF не трогается.
- **Видео** перекодируется в MP4 (H.264 и AAC, CRF 28) через `ffmpeg`, он должен быть в `PATH`. Это может занять время, а размер иногда даже вырастает. Временный файл удаляется после отправки.

Миниатюры и thumbhash SDK не создаёт.

### Скачивание

```python
bot.download_file("CHAT_ID", "FILE_ID", destination="received.bin")
```

Файл записывается потоком и никогда не перезаписывает существующий. Без `destination` вернутся байты. Принимаются только ссылки вида `/v1/chat-files/{uuid}` на вашем сервере. В обработчике проще: `attachment.download("путь")`.

> **Безопасность.** Имя файла приходит от пользователя. Не используйте его как локальный путь без проверки.

### Вложения чата по категориям

```python
result = bot.get_media("CHAT_ID", category="0", limit=20)
```

Параметр `category` в SDK аннотирован как `str` и передаётся в query без преобразования или проверки по списку. Числовые категории клиента сайта передавайте строками:

| `category` | Категория клиента сайта |
|---|---|
| `"0"` | Медиа (фото и видео) |
| `"1"` | Файлы |
| `"2"` | Музыка |
| `"3"` | Голосовые сообщения |

Соответствие взято из [#42](https://github.com/itd-social/CHATBOT-SDK/issues/42), без повторной проверки бандла и сервера. SDK передаст и прежние строковые значения, но их приём сервером не подтверждён. `before` и `limit` уходят в запрос, только если заданы.

### Эксперимент: своё имя и MIME

`send_file` и `upload_file` позволяют отдельно задать `filename` и `mime`:

```python
bot.send_file("CHAT_ID", "music.mp3", filename="photo.png", mime="video/mp4")
```

SDK отправит байты как есть, ничего не конвертируя. Сервер может отклонить такой файл, а приложения покажут его по-разному. Это эксперимент, на результат не рассчитывайте.

> **Если загрузка сорвалась,** на сервере может остаться недогруженный файл. Автоматическая очистка не подтверждена. Если пришла ошибка [`UploadQuotaError`](RATE_LIMITS.md#лимит-загрузок), сначала разберитесь с незавершёнными загрузками.

## Реакции и typing

### Реакции

```python
bot.add_reaction("CHAT_ID", "MESSAGE_ID", "👍")

@router.reaction()
def changed(ctx):
    print(ctx.chat_id, ctx.message_id, ctx.event.get("reactions"))
```

`add_reaction` добавляет эмодзи к уже выбранным. Если нужно заменить весь набор, используйте `set_reactions` (с `expected_version` и уникальным `operation_id`). При конфликте версий сервер может ответить 409, повтора нет.

События приходят и от собственных реакций бота, поэтому следите, чтобы обработчик не запускал сам себя по кругу.

### Typing

Диспетчер **сам** показывает «печатает…», если обработчик работает дольше 0,5 секунды, и обновляет статус каждые 4 секунды. Быстрые ответы идут без лишних запросов.

```python
Dispatcher(bot, self_user_id="...", auto_typing=False)  # выключить
Dispatcher(bot, self_user_id="...", typing_delay=0)     # показывать сразу
```

Для своих долгих задач есть контекстный менеджер:

```python
from itd_bot import ChatAction

with bot.chat_action(chat_id):  # typing, пока идёт блок
    answer = slow_work()

with bot.chat_action(chat_id, ChatAction.UPLOAD_VIDEO, progress=0.0) as action:
    for step in range(1, 11):
        do_part(step)
        action.progress = step / 10
```

Доступные статусы: `TYPING`, `RECORD_VOICE`, `RECORD_VIDEO`, `UPLOAD_PHOTO`, `UPLOAD_VIDEO`, `UPLOAD_VOICE`, `UPLOAD_DOCUMENT`. `progress` (число от 0 до 1) работает только для `upload_*`, иначе будет `ValueError`. Если фоновая отправка статуса не удалась, повторов нет, а ошибка сохранится в `action.error`.

> **Не видно typing?** Проверьте, не скрыт ли у аккаунта бота статус «онлайн»: из-за этого индикатор может не показываться.

Примеры: [`examples/chat_actions.py`](../examples/chat_actions.py), а в тестовом боте есть `/wait 15` и `/react`.

## Профили пользователей

```python
user = bot.get_user("@example")       # по ID или нику
me = bot.get_me()                      # профиль самого бота

@router.command("profile")
def profile(ctx):
    user = ctx.get_sender()
    ctx.reply(f"Привет, {user.display_name or user.username or 'друг'}!")
```

У `User` есть `id`, `username`, `display_name`, `avatar`, `banner`, `bio`, `is_verified`, `is_private`, `followers_count`, `following_count`, `posts_count`, `is_following`, `is_followed_by`, `can_message`, `online`, `last_seen` и другие поля. Исходный ответ сервера всегда доступен в `user.raw`.

Чтобы получить баннер или закреплённый пост:

```python
user.banner_url                       # адрес или None
user.download_banner("banner.png")    # скачать (не перезаписывает файл)

post = user.pinned_post               # отдельный запрос, может быть None
if post is not None:
    post.share("CHAT_ID", text="Закреплённый пост")
```

Подписки: `user.is_followed_by` показывает, подписан ли пользователь на бота, а `bot.get_follow_status([user.id])` — наоборот.

> **Хорошо знать.** Кэша нет: каждый вызов делает запрос. Необязательные поля могут быть `None`, и `None` не значит `False`. Доступность данных зависит от приватности пользователя.

## События и надёжность

Обычно `run_polling` делает всё нужное, но полезно понимать, как он устроен.

- Бот периодически спрашивает у сервера новые события (`get_updates`) и двигает **курсор**.
- Курсор сохраняется только после того, как обработан **весь** пакет событий (пропущенные по [решению об ошибке](#если-обработчик-упал) тоже считаются обработанными). Поэтому при сбое события могут прийти повторно.
- Первый запуск берёт текущий курсор и пропускает прошлое. Если старые события важны, сначала сверьте историю.
- Курсор ИТД — не Telegram `update_id`, и гарантий «ровно один раз» нет.

```python
router.run_polling(state_path=".bot-state.json")               # курсор в файле
router.run_polling(since=cursor, on_checkpoint=save_cursor)    # или хранить самому
```

Курсор привязан к аккаунту и серверу. Не используйте один файл в нескольких процессах. Вызов без `since` и `state_path` вернёт `ValueError`, а `since` вместе с уже существующим файлом состояния тоже запрещён: выберите что-то одно.

### Защита от повторной обработки

По умолчанию `Dispatcher` запоминает последние 4096 успешно обработанных входящих сообщений. Повтор одного `message_id` в том же чате, аккаунте и на том же сервере пропускается до отметки прочтения и вызова обработчика. Это исправление ошибки повторной обработки пакетов; прежний режим можно вернуть:

```python
router = Dispatcher.from_bot(bot, dedup_capacity=8192)  # больше успешных сообщений в памяти
router = Dispatcher.from_bot(bot, deduplicate=False)   # прежняя обработка дублей
```

В кэш попадают только сообщения, обработка которых завершилась без исключения. Если `mark_read` или обработчик упал, сообщение можно обработать снова. При повторе пакета `new_messages` уже успешные сообщения пропускаются, а оставшиеся обрабатываются по порядку. Реакции, правки и удаления эта защита не подавляет.

Кэш ограничен по принципу LRU: старые записи вытесняются, а перезапуск процесса очищает память. Защита не гарантирует «ровно один раз» после перезапуска, вытеснения записи или частичного сбоя самого обработчика. Его действия до исключения могли уже выполниться, поэтому `ErrorAction.RETRY` по-прежнему требует осторожности.

Свое хранилище передайте через `dedup_store`. `MemoryDedupStore(capacity=4096)` — стандартная реализация; аргумент `dedup_capacity` применяется только к ней. Протокол `DedupStore` использует ключ `(base_url, self_user_id, chat_id, message_id)`:

| Метод | Контракт |
|---|---|
| `claim(key) -> bool` | Атомарно резервирует сообщение. Для успешного дубля возвращает `False`; параллельный вызов ждёт завершения или освобождения первой обработки |
| `complete(key)` | Запоминает успешную обработку, освобождает резервирование и будит ожидающих |
| `release(key)` | Освобождает неуспешную попытку и разрешает новую обработку |

Хранилище должно быть потокобезопасным и ограничивать число завершённых записей. Его ошибка выходит из `handle()` в существующую политику `on_error`; после ошибки сохранения обработчик мог уже выполнить свои действия. Сроком жизни внешнего хранилища управляете вы, `Dispatcher.close()` его не очищает. Пример: [`examples/dedup_store.py`](../examples/dedup_store.py).

### Быстрые обновления и параллельная работа

```python
router.run_polling(state_path=".bot-state.json", websocket=True, workers=4)
```

- **`websocket=True`** (нужен `itd-chatbot-sdk[websocket]`) использует WebSocket как сигнал «появилось новое»: бот реагирует быстрее, но события всё равно берутся по курсору. Если WebSocket замолчит, запасной опрос по `interval` продолжит работу. На живом ИТД режим не проверялся.
- **`workers=4`** обрабатывает разные чаты параллельно внутри одного пакета, порядок внутри чата сохраняется. Курсор сохраняется и следующий пакет запрашивается только после завершения всех обработчиков текущего пакета. Медленный обработчик задерживает события из следующих пакетов, даже если они относятся к другим чатам. По умолчанию `workers=1`: все обработчики выполняются последовательно. Общие данные (словари, счётчики, соединения с БД) при параллельной работе защищайте блокировками.

Тяжёлые операции (внешние API, нейросети) выносите в свою очередь или отдельный поток, чтобы обработчик быстро возвращал управление. При этом SDK считает событие обработанным после возврата из обработчика и не ждёт фоновой задачи: её сохранение, ошибки, порядок и защиту от дублей организуйте сами. Очереди по чатам внутри SDK запланированы в [#22](https://github.com/itd-social/CHATBOT-SDK/issues/22), сейчас их нет.

Вручную события можно читать через `get_updates` и `websocket_events()`. В этом случае typing и отметки прочтения вы делаете сами, а два источника лучше не смешивать без дедупликации.

### Сбои сети

Если `get_updates` не отвечает (обрыв, таймаут) или сервер отвечает 500, 502, 503 или 504, бот ждёт и повторяет **тот же** запрос с тем же курсором. Пауза растёт 1, 2, 4… секунд до 60, а после удачного запроса сбрасывается. В лог попадает предупреждение с классом ошибки, HTTP-статусом, номером попытки и паузой, но без адреса, заголовков и тела ответа.

```python
router.run_polling(state_path=".bot-state.json", retry_initial_delay=1.0, retry_max_delay=60.0)
```

Остальные ошибки опроса (`ResetRequired`, 401, 403, 404, `ProtocolError`, `SessionStorageError`) завершают `run_polling` как раньше. `RateLimitError` по-прежнему обрабатывается своей паузой из [лимитов](RATE_LIMITS.md#если-пришёл-429).

Отдельно `Bot(..., get_retries=2)` повторяет любой **GET** после такого же сбоя: два раза с паузами около 0,5 и 1 секунды. Каждая попытка проходит через лимитер. `get_retries=0` отключает повторы, после последней неудачи вы получите исходное исключение. Запись (POST, PUT, PATCH, DELETE), скачивание файлов и баннеров не повторяются: после обрыва неизвестно, выполнил ли сервер запрос. Ошибки обновления сессии после 401 тоже не повторяются.

### Если обработчик упал

По умолчанию бот не падает: ошибка из обработчика пишется в лог (`ERROR`, только класс ошибки и тип события), событие пропускается, курсор идёт дальше. Решение можно взять в свои руки:

```python
import logging

import httpx

from itd_bot import ErrorAction

@router.on_error()
def handle_error(error, event):
    logging.error("Сбой в событии %s: %s", event.get("type"), type(error).__name__)
    if isinstance(error, httpx.TransportError):
        return ErrorAction.RETRY  # только если повтор безопасен
    return ErrorAction.SKIP
```

| Решение | Что произойдёт |
|---|---|
| `SKIP` или `None` | Событие пропущено, обработка продолжается |
| `RETRY` | Тот же обработчик вызывается снова до `handler_retries` раз (по умолчанию 3) с паузами 1, 2, 4… секунд, потом событие пропускается с записью в лог |
| `STOP` | Исключение выходит из `run_polling`, курсор пакета не сохраняется, после перезапуска события придут снова |

Хук получает исключение и исходное событие (словарь). Поэтому `traceback` и свои логи вы пишете сами; SDK их не пишет, потому что в тексте ошибки могут оказаться сообщения пользователей. Ошибка внутри самого хука не скрывается и завершает `run_polling`. `KeyboardInterrupt` и `SystemExit` хук не видит. При `workers > 1` хук вызывается из рабочих потоков.

- Порядок событий внутри чата сохраняется при любом решении. Ошибка в одном чате не отменяет и не повторяет обработку в других.
- `STOP` не прерывает уже начатые обработчики в других чатах, но новые события не запускаются.
- Хук можно передать и напрямую: `router.run_polling(..., on_error=handle_error)`.

> **Осторожно.** `RETRY` может **продублировать** отправку: сервер не подтвердил идемпотентность, а «ровно один раз» SDK не гарантирует. Включайте повтор только для безопасных обработчиков.

> **Хорошо знать.** Раньше исключение обработчика завершало бота. Теперь событие пропускается и **теряется**. Хотите прежнее поведение? Верните `ErrorAction.STOP`. Всё это проверено только тестами с подменой сервера, на живом ИТД не проверялось.

**Сбой отметки прочтения.** В режиме `blocking` (он включён по умолчанию) отметка идёт до обработчика, поэтому обработчик ещё не начал работу. Если отметка не удалась из-за сети, ошибки 500, 502, 503, 504 или ответа 429, событие не теряется: бот ждёт (1, 2, 4… секунд, потолок 60) и запрашивает **тот же** пакет заново. Уже успешные сообщения пропускаются, пока остаются в кэше [дедупликации](#защита-от-повторной-обработки). При отключении кэша, перезапуске или вытеснении записи обработчик может получить их повторно. Постоянная ошибка (например, чат удалён, ответ 404) идёт в `on_error` как обычная: по умолчанию событие пропускается. Если нужен повтор для `RateLimitError` из самого обработчика, верните `RETRY` для него в хуке сами: SDK не знает, безопасно ли повторять ваш код.

### Остановка бота

```python
router.run_polling(state_path=".bot-state.json")  # Ctrl+C или SIGTERM остановят мягко
```

Первый `Ctrl+C` или `SIGTERM` (в Windows ещё `Ctrl+Break`) — просьба остановиться: бот дорабатывает текущий пакет, сохраняет курсор и возвращается из `run_polling` без исключения. Если обработчик долго работает, остановка ждёт его. Второй `Ctrl+C` поднимет `KeyboardInterrupt` сразу, и обработчики прервутся на полуслове. Прежние обработчики сигналов `run_polling` возвращает при выходе.

Обработчики сигналов ставятся только в главном потоке. Запускаете бота в другом потоке или хотите остановить его из кода? Передайте свой `threading.Event`:

```python
import threading

stop = threading.Event()
threading.Thread(
    target=router.run_polling,
    kwargs={"state_path": ".bot-state.json", "stop": stop, "handle_signals": False},
).start()

stop.set()  # пакет будет доработан, курсор сохранён
```

`handle_signals=False` отключает сигналы совсем (например, если ими управляет ваша программа). Сервисы вроде systemd или Docker убивают процесс по таймауту, поэтому подберите его с запасом на ваш самый долгий обработчик. Реальные сигналы ОС и Windows проверялись только тестами с подменой обработчиков.

## Ошибки

```python
from itd_bot import APIError, ResetRequired

try:
    router.run_polling(state_path=".bot-state.json")
except ResetRequired:
    print("Сервер потерял часть событий: сверьте состояние с чатами")
except APIError as error:
    print(f"ИТД вернул HTTP {error.status}, код {error.code}")
```

| Ошибка | Что значит и что делать |
|---|---|
| `APIError` | Ответ сервера с ошибкой: смотрите `status`, `code`, `errors`, `retry_after` |
| `RateLimitError` | Ответ 429: подождите `error.retry_after_seconds`, см. [лимиты](RATE_LIMITS.md) |
| `UploadQuotaError` | Закончился бюджет загрузок |
| `ResetRequired` | Сервер не может выдать все события с вашего курсора. Восстановите состояние и только потом выберите новый курсор. Просто сдвинуть курсор вперёд нельзя: часть событий потеряется |
| `ProtocolError` | Ответ сервера не похож на ожидаемый |
| Ошибки `httpx` | Сеть или таймаут. При опросе и в GET бот повторяет запрос сам, см. [сбои сети](#сбои-сети). Если это была отправка, не повторяйте её вслепую |

Для долгой работы настройте наблюдение за процессом. Сбои сети при опросе бот переживает сам, а ошибки обработчиков по умолчанию пропускает. Остальное (`ResetRequired`, ошибка сессии, `STOP` из хука) завершает `run_polling`: разберите причину и только потом перезапустите бота.

### Коды ошибок сервера

```python
from itd_bot import APIError

try:
    bot.send_message("CHAT_ID", "Привет!")
except APIError as error:
    if error.code == "nuksta_required":
        print("Проверьте подписку ИТД НУКСТА у аккаунта бота")
    elif error.code in {"blocked", "messages_closed"}:
        print("Отправка этому получателю недоступна")
    else:
        raise
```

| `error.code` | Что означает и как обработать |
|---|---|
| `nuksta_required` | Для отправки нужна подписка «ИТД НУКСТА» у аккаунта бота. Проверьте подписку; автоматический повтор причину не устранит |
| `blocked` | Отправка запрещена из-за блокировки. Прекратите автоматические отправки этому получателю и разберите причину блокировки |
| `messages_closed` | Сообщения получателя закрыты. Не повторяйте отправку без изменения доступности переписки |
| `RATE_LIMIT_EXCEEDED` | Превышен лимит: SDK выдаёт `RateLimitError` при HTTP 429 или локальной блокировке. Учитывайте `retry_after_seconds`; код сервера может отличаться |
| `UPLOAD_QUOTA_EXCEEDED` | Бюджет загрузок исчерпан: при HTTP 429 SDK выдаёт `UploadQuotaError`. Не начинайте новые загрузки, пока не разобрались с незавершёнными, см. [лимит загрузок](RATE_LIMITS.md#лимит-загрузок) |

Первые три кода описаны в [#42](https://github.com/itd-social/CHATBOT-SDK/issues/42); в этой работе они не проверялись на сервере. SDK передаёт код ответа в `APIError.code` без отдельного класса для каждого кода. Проверяйте `code`, не привязываясь к непроверенному HTTP-статусу; неизвестный код или `None` тоже допустимы.

Области `ip_flood`, `global_flood`, `new_recipients_hour` и `new_recipients_day` читаются отдельно из заголовка `X-RateLimit-Scope` и доступны как `RateLimitError.scope`. Это не значения `error.code`, см. [обработку 429](RATE_LIMITS.md#если-пришёл-429).

### Тестовый бот

[`examples/test_bot.py`](../examples/test_bot.py) — интерактивный бот для тестового аккаунта. Он читает все сообщения, но выполняет команды только от пользователя `ITD_TESTER_ID`. Команда `/help` покажет всё, что он умеет, в том числе `/file`, `/download FILE_ID` и `/api METHOD /api/путь [JSON]`.

> **Осторожно.** `/api` может изменять данные от имени бота. Давайте доступ только доверенному тестировщику и используйте тестовый аккаунт.

```sh
export ITD_TOKEN="ТОКЕН_БЕЗ_BEARER"
export ITD_SELF_USER_ID="ID_АККАУНТА_БОТА"
export ITD_TESTER_ID="ID_ТЕСТИРОВЩИКА"
python examples/test_bot.py
```

Нужные ID видны в `get_chats()` (`other_user_id` для личного чата). Курсор бот хранит в `.itd-test-bot-cursor`; для другого аккаунта задайте свой `ITD_CURSOR_FILE`. Короткий токен истекает, при 401 нужен новый.
