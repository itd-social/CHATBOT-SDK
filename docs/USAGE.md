# Руководство разработчика

Python-клиент для мессенджера ИТД, восстановленный по собранному веб-клиенту из предоставленного архива. На тестовом аккаунте проверены обмен сообщениями, загрузка и скачивание файлов, несколько обновлений access-токена и подключение WebSocket; серверный исходный код и полная спецификация не предоставлены. Это клиент пользовательского API, а не подтверждённый официальный Bot API. Аккаунт и его права определяются переданным Bearer-токеном.

## Установка

Python 3.10+. Установите пакет в окружение вашего бота:

```bash
python -m pip install itd-chatbot-sdk
```

В примерах ниже используется короткоживущий токен `ITD_TOKEN`. Для длительной сессии используйте `Bot.from_refresh_token(...)` и [инструкцию по авторизации](AUTH.md). Вход по паролю не реализован. В режиме refresh SDK при HTTP 401 обновляет сессию и повторяет запрос один раз, кроме multipart-запросов; при сетевой ошибке запрос не повторяется автоматически и результат записи может быть неизвестен.

```python
import os
from itd_bot import Bot

with Bot(os.environ["ITD_TOKEN"]) as bot:
    chats = bot.get_chats(limit=20)
    print(chats)
    bot.send_message("CHAT_ID", "Привет!")
```

В следующих фрагментах `bot` — открытый экземпляр `Bot`, а `router` — связанный с ним `Dispatcher`. `cursor` и `save_cursor` показаны в полностью запускаемом [примере первого бота](GETTING_STARTED.md).

`base_url` по умолчанию — `https://xn--d1ah4a.com`, запросы отправляются в `/api/v1/messenger`. Можно задать другой адрес через `Bot(token, base_url="https://...")`. Ответы большинства методов — обычные словари и списки JSON с исходными именами полей; это сохраняет неизвестные поля и не навязывает неподтверждённую схему. Ошибки HTTP представлены `APIError` с полями `status`, `code`, `errors`, `retry_after`; ошибки сети и таймаута — исключениями `httpx`. Неправильный формат ответа журнала вызывает `ProtocolError`.

## Профиль пользователя

`bot.get_user(user_id_or_username)` получает профиль по ID или нику с необязательным `@`; `bot.get_me()` получает профиль аккаунта бота. Оба метода возвращают `User`. В обработчике команды `ctx.get_sender()` получает профиль отправителя текущего сообщения:

```python
@router.command("profile")
def profile(ctx):
    user = ctx.get_sender()
    name = user.display_name or user.username or "друг"
    ctx.reply(f"Привет, {name}! Подписчиков: {user.followers_count}")

user = bot.get_user("@example")
print(user.id, user.username, user.display_name)
print(user.bio, user.avatar, user.banner, user.pin)
print(user.raw)
```

Доступны поля `id`, `username`, `display_name`, `avatar`, `banner`, `bio`, `is_verified`, `is_private`, `pin`, `has_nuksta`, `pinned_post_id`, `wall_access`, `likes_visibility`, `followers_count`, `following_count`, `posts_count`, `is_following`, `is_followed_by`, `created_at`, `can_message`, `online`, `last_seen`. В `user.raw` остаётся исходный ответ сервера, включая неизвестные поля. `pin`, `avatar`, `banner` и `last_seen` сохраняют исходную структуру; даты не преобразуются.

`user.banner_url` возвращает адрес баннера или `None`. `user.download_banner("banner.png")` скачивает его с CDN ИТД в новый файл без передачи токена; существующий файл не перезаписывается. Если баннера нет, метод сообщает об ошибке.

`user.pinned_post` получает закреплённый пост отдельным HTTP-запросом, либо возвращает `None`, если поста нет. Свойства `post.id`, `post.content`, `post.author`, `post.attachments` и `post.raw` дают доступ к данным. `post.share(chat_id, text="...")` отправляет пост в чат как вложение поста. Формат пересылки обнаружен в веб-клиенте и проверен локально; живую отправку необходимо проверить отдельно.

```python
post = user.pinned_post
if post is not None:
    print(post.content, post.author, post.raw)
    post.share("CHAT_ID", text="Закреплённый пост")
```

`user.is_followed_by` показывает, подписан ли пользователь на аккаунт бота, если сервер вернул это поле. `bot.get_follow_status([user.id])` возвращает обратное направление: подписан ли аккаунт бота на пользователя. При отсутствии информации не считайте `None` значением `False`.

Каждый вызов делает HTTP-запрос; автоматического кэша нет. Необязательные поля могут отсутствовать и тогда равны `None`. Доступность данных зависит от сервера и приватности; `False` и `0` сохраняются как получены. `APIError` сообщает об ошибке сервера, а отсутствие корректного `id` вызывает `ProtocolError`.

## События и надёжность

`get_updates(since)` делает обычный HTTP GET `/updates`, не long polling. Результат содержит `events`, `next_event_seq`, `reset_required`. Указывайте сохранённый курсор и сохраняйте новый только после успешной обработки **всего** пакета. При аварии пакет может прийти повторно: обработчики и побочные эффекты должны быть идемпотентны. Конкурирующие экземпляры бота требуют собственной координации. `Bot.poll` вызывает `on_checkpoint` после пакета, сразу запрашивает следующий пакет, если предыдущий был непустым и сдвинул курсор, а иначе делает паузу `interval`; исключение обработчика останавливает цикл и не подтверждает пакет. Курсор хранит само приложение. `reset_required` вызывает `ResetRequired`: восстановите состояние из чатов/истории и только после этого самостоятельно выберите новый курсор; SDK не пропускает потерянные события автоматически.

Для первого запуска веб-клиент получает `event_seq` из списка чатов. Его использование как начального курсора намеренно пропускает прошлые события; если они важны, сначала согласуйте историю с состоянием приложения. Наличие/корректность курсора обязательно проверьте. Нельзя считать курсор Telegram `update_id` или предполагать гарантии exactly-once. Для живых событий доступен `websocket_events()` после установки `python -m pip install "itd-chatbot-sdk[websocket]"`. Он отправляет ping и закрывает соединение при завершении генератора, но не восстанавливает пропущенные события автоматически: после разрыва сверяйте состояние через `get_updates` и сохранённый курсор. Не запускайте оба источника без дедупликации. Самый быстрый безопасный вариант — `poll(..., websocket=True)`: WebSocket используется только как сигнал «есть новое», а события читаются из `/updates` по курсору, поэтому задержка ответа равна одному HTTP-запросу вместо паузы опроса. Безопасность обеспечивает запасной опрос по `interval`; запросы за обновлениями начинаются не чаще `min_fetch_interval` (0,2 секунды). На живом ИТД режим не проверялся: неизвестно, присылает ли сервер кадр на каждое новое сообщение. Если нет, поведение такое же, как у обычного опроса с интервалом `interval`. При `workers > 1` обработчики вызываются параллельно из разных потоков: общее изменяемое состояние (словари, счётчики, соединения с БД) защищайте блокировками.

Пример эхо-бота с сохранением курсора — в `examples/echo.py`. Для настоящего бота сохраняйте курсор и результаты обработки в надёжном хранилище, обрабатывайте 429 с учётом `Retry-After` и прекращение действия сессии. Точное поведение дедупликации `client_message_id` сервером не установлено: не полагайтесь на него как на гарантию.

## Методы

- Чаты: `get_chats`, `get_chat`, `get_unread_count`, `create_direct_chat`, `accept_chat`, `set_pinned`, `set_muted`, `mark_unread`, `delete_chat`, `clear_history`.
- Сообщения: `get_messages`, `get_messages_around`, `send_message`, `send_message_to_user`, `edit_message`, `delete_messages`, `forward_messages`, `mark_read`, `send_action`.
- Реакции: `get_reaction_catalog`, `get_reactions`, `set_reactions`.
- Прочее: `get_presence`, `get_presence_many`, `get_media`, `get_file_links`, `mark_voice_heard`, `get_heard_messages`, `get_updates`.
- `request(method, path, params=..., json=...)` предоставляет доступ к другим **messenger**-маршрутам с тем же Bearer-токеном. Передаваемые ID кодируются как отдельные сегменты пути. Ответы и входные структуры `attachments`, `entities` и `reactions` остаются сырыми JSON: серверные ограничения в бандле подтверждены не полностью.

## Автоматический typing и реакции

`Dispatcher` по умолчанию показывает `typing`, если зарегистрированный обработчик сообщения или события работает дольше `typing_delay` (0,5 секунды), и обновляет его каждые 4 секунды до завершения обработки. Быстрые ответы уходят без лишнего запроса `typing`; `typing_delay=0` возвращает отправку до запуска обработчика. Неудача отправки записывается в стандартный Python logging и не останавливает обработчик. Отображение после ответа зависит от времени жизни индикатора на сервере. При проверке пользователь установил, что скрытый статус онлайн мешал отображению индикатора; учитывайте настройки приватности аккаунта бота. Для особых случаев можно задать `Dispatcher(bot, self_user_id="...", auto_typing=False)` или изменить `typing_interval`. Автоматическое поведение относится к обработчикам Dispatcher; при ручной обработке событий через `get_updates` или `websocket_events` используйте `send_action` самостоятельно. Вызов `send_action` не повторяется SDK автоматически.

```python
bot.add_reaction(chat_id, message_id, "\U0001f44d")

@router.on_event("message_reactions")
def changed(event):
    print(event["chat_id"], event["message_id"], event.get("reactions"))
```

Получить каталог и текущее состояние можно через `get_reaction_catalog` и `get_reactions`; `set_reactions` заменяет весь набор выбранных реакций и принимает `expected_version` и уникальный `operation_id`. `add_reaction` получает состояние и добавляет emoji, сохраняя выбранные реакции; ограничения и типы проверяет сервер. События могут отражать и собственные действия бота, поэтому обработчики должны предотвращать бесконечные циклы. Уведомления о реакции доступны в журнале событий при условии, что сервер их присылает; точные гарантии доставки не подтверждены.

В тестовом боте `/wait 15` позволяет наблюдать typing при долгой работе, а `/react` пытается поставить реакцию.

## Форматирование текста

`Text` строит текст и список `entities` без Markdown и экранирования. Смещения вычисляются в единицах UTF-16, как в веб-клиенте ИТД, поэтому эмодзи учитываются правильно.

```python
from itd_bot import Text

content = (Text("Привет \U0001f44b ")
           .bold("жирный")
           .add(" и ")
           .italic("курсив")
           .add(". ")
           .link("Открыть сайт", "https://example.com"))
bot.send_formatted("CHAT_ID", content)
```

Доступны `bold`, `italic`, `underline`, `strike`, `code`, `spoiler`, `link`. Стиль можно комбинировать: `Text().add("текст", styles=("bold", "italic"))`. Для ручной отправки `text, entities = content.build()`; передайте их в `send_message`. Конструктор создаёт не более 50 сущностей, как допускает проверка веб-клиента. Рендеринг и сочетания стилей на сервере пока проверены локальными тестами, не живым сообщением.

## Файлы

```python
result = bot.upload_file("report.pdf")
bot.send_message("CHAT_ID", "Отчёт", attachments=[result["fileId"]])
bot.send_file("CHAT_ID", "report.pdf", text="Отчёт")
```

Поддерживаются произвольные типы файлов, если сервер их принимает; веб-клиент ограничивает размер 2 ГиБ и запрещает пустые файлы. Данные отправляются частями по 5 МиБ, до одной части одновременно находится в памяти. `metadata` передаёт необязательные поля финализации (`width`, `height`, `durationMs`, `waveform`, `thumbhash`, `thumb`); `on_progress(sent, total)` сообщает прогресс. SDK не преобразует медиа и не создаёт миниатюры. Повторное использование `fileId`, ограничения типов и время жизни файлов зависят от сервера.

### Фото, видео и музыка

```python
bot.send_photo("CHAT_ID", "photo.png", caption="Фото")
bot.send_video("CHAT_ID", "video.mp4", caption="Видео")
bot.send_music("CHAT_ID", "track.mp3", caption="Музыка")
```

По умолчанию эти методы отправляют исходные байты. Доступен также `send_audio` как синоним `send_music`. В обработчике команды можно ответить через `ctx.reply_photo(...)`, `ctx.reply_video(...)`, `ctx.reply_music(...)` или `ctx.reply_file(...)`; ответ будет привязан к входящему сообщению. `reply_file`, как и `send_file`, принимает подпись через `text`.

Для сжатия фото установите `python -m pip install "itd-chatbot-sdk[images]"` и укажите `compress=True`:

```python
bot.send_photo("CHAT_ID", "photo.png", caption="Фото", compress=True)
```

Фото преобразуется в JPEG: длинная сторона не больше 1920 пикселей, качество 70; прозрачность заменяется белым фоном. GIF сохраняется без перекодирования. Указать другое имя и MIME для экспериментов можно при отправке без сжатия. SDK передаёт размеры обработанного фото, но не создаёт миниатюру или thumbhash.

`bot.send_video("CHAT_ID", "video.mov", compress=True)` отдельно перекодирует видео в MP4 через `ffmpeg`, который должен быть установлен и доступен в PATH. Используются H.264 и AAC, CRF 28. Это возможность SDK; в исследованном веб-клиенте перекодирование видео не обнаружено. Сжатие может занять время и место во временной папке, уменьшить качество или увеличить размер; после отправки временный файл удаляется. Для отправки без перекодирования используйте `compress=False`.

### Эксперимент: произвольные MIME и имя файла

`send_file` и `upload_file` позволяют независимо указать содержимое файла, MIME и имя, под которым файл будет сохранён. Например, можно отправить музыку, объявив её видео и задав имя с расширением PNG:

```python
bot.send_file(
    "CHAT_ID",
    "music.mp3",
    filename="photo.png",
    mime="video/mp4",
    text="Эксперимент",
)
```

SDK передаст исходные байты без перекодирования или сжатия. `mime` уходит на этапе создания загрузки, а `filename` - при её завершении. Для загрузки без отправки используйте `bot.upload_file("music.mp3", filename="photo.png", mime="video/mp4")`; результат содержит `fileId`, который можно передать в `send_message` через `attachments=[file_id]`.

Это экспериментальная возможность: сервер может отклонить файл или параметры, а приложения могут показывать его по-разному или не суметь открыть. Имя и MIME не превращают содержимое в другой формат. Обычные ограничения SDK по размеру и непустому файлу сохраняются. Передача неподтверждённого `fileId` и работа произвольных значений `metadata` зависят от сервера.

```python
bot.download_file("CHAT_ID", "FILE_ID", destination="received.bin")
```

Скачивание открывает файловую сессию и использует cookie клиента. Сохранение в файл потоковое и не перезаписывает существующий файл. Метод поддерживает ссылки `/v1/chat-files/{uuid}` на настроенном сервере; иные адреса отклоняются. На тестовом аккаунте проверено скачивание существующего вложения. При сбое загрузки или отправки может остаться загруженный файл; автоматическая очистка не подтверждена.

## Команды

```python
from itd_bot import Dispatcher

router = Dispatcher(bot, self_user_id="BOT_USER_ID", username="bot_name")

@router.command("start")
def start(ctx):
    ctx.reply("Привет! Напишите /help")

@router.command("help")
def help_command(ctx):
    ctx.reply("Команды: /start, /help")

@router.command("echo")
def echo(ctx):
    ctx.reply(ctx.args or "Добавьте текст после команды")

router.run_polling(since=cursor, on_checkpoint=save_cursor)
```

`/start` и другие команды регистрируются приложением; встроенных ответов SDK не создаёт. Команды маршрутизируются только в начале текста, аргументы доступны как `ctx.args`. Суффикс `@username` учитывается только при совпадении с заданным именем. `self_user_id` обязателен, чтобы не отвечать самому себе. Dispatcher сначала вызывает `mark_read` для каждого входящего сообщения, включая сообщения без текста и команды для другого бота, и только затем запускает обработчик. Если отметка прочтения не удалась, обработка прерывается и курсор пакета не сохраняется. `@router.on_message` регистрирует обработчик остальных сообщений с аргументами `(event, message)`. Это локальный механизм SDK, а не подтверждённая регистрация команд на сервере ИТД. См. готовый [пример](../examples/commands.py).

## Упрощённый запуск и контекст

`Dispatcher.from_bot(bot)` получает профиль бота и настраивает защиту от ответов самому себе. `router.run_polling(state_path=".bot-state.json")` сохраняет курсор после успешной обработки пакета. При первом запуске берётся текущий курсор, поэтому старые события пропускаются; при повторном запуске чтение продолжается с сохранённого значения. Состояние привязано к аккаунту и адресу сервера. Не используйте один файл одновременно в нескольких процессах; добавьте его и временные файлы в `.gitignore` вашего бота. Повторная доставка после сбоя и `ResetRequired` по-прежнему требуют обработки.

```python
router = Dispatcher.from_bot(bot)

@router.message()
def on_message(ctx):
    print(ctx.sender_id, ctx.chat_id, ctx.text)
    sent = ctx.reply_message("Получено")
    sent.edit("Обработано")

@router.photo()
def on_photo(ctx):
    for photo in ctx.photo:
        print(photo.filename, photo.mime, photo.size)

router.run_polling(state_path=".bot-state.json")
```

`ctx.attachments` содержит все вложения, `ctx.photo` - список вложений с MIME `image/*`; `attachment.download(path)` скачивает файл чата, а `attachment.raw` содержит исходные данные. Фотообработчик имеет приоритет перед `message()` для сообщений с фотографиями; зарегистрированные команды обрабатываются раньше обоих. При этом `ctx.message` и `ctx.event` остаются исходными словарями. Старый `@router.on_message` с аргументами `(event, message)` также поддерживается; нельзя регистрировать его одновременно с `message()`.

`ctx.reply()` по-прежнему возвращает исходный словарь. Используйте `ctx.reply_message()`, чтобы получить объект с методами `edit` и `delete`. Также доступны `ctx.react`, `ctx.remove_reaction`, `ctx.delete_message`, `ctx.forward_to` и `ctx.is_subscribed()`. Последний делает запрос профиля и возвращает `True`, `False` или `None`; `None` означает, что сервер не сообщил статус.

`@router.reaction()`, `@router.edited()` и `@router.deleted()` принимают контекст события с полями `chat_id`, `message_id`, `reactions` и исходным `event`. При массовом удалении идентификаторы доступны в `ctx.event["message_ids"]`. Прежний `on_event` остаётся доступным.

## Обработка обычного сообщения

`on_message` вызывается для сообщений без зарегистрированной команды. Аргументы — исходное событие и словарь сообщения. Используйте ID сообщения из `message["message_id"]`, чтобы ответить на него:

```python
@router.on_message
def on_message(event, message):
    text = message.get("text")
    if text:
        bot.send_message(event["chat_id"], f"Вы написали: {text}", reply_to_id=message["message_id"])
```

Если сообщение содержит вложения, в `message.get("attachments", [])` могут присутствовать объекты с `fileId`, `filename` и `mime`. Получите `fileId` конкретного вложения и передайте вместе с ID чата в `download_file`. Не используйте имя, присланное пользователем, как локальный путь без проверки.

## Обработка ошибок

```python
from itd_bot import APIError, ResetRequired

try:
    router.run_polling(since=cursor, on_checkpoint=save_cursor)
except ResetRequired:
    print("Нужно восстановить состояние из чатов и истории")
except APIError as error:
    print(f"ИТД вернул HTTP {error.status}; код: {error.code}")
```

`ResetRequired` нельзя безопасно исправить простым переходом на новый курсор: часть событий может быть потеряна. При 429 учитывайте `error.retry_after`. Ошибки сети представлены исключениями `httpx`; при неясном результате отправки не повторяйте её вслепую. Для длительного запуска предусмотрите наблюдение за процессом и перезапуск после анализа ошибки.

Автоматические тесты используют локальный транспорт. Отдельно на тестовом аккаунте проверены получение и отправка текстовых сообщений, загрузка одного текстового файла и WebSocket ping/pong. Отправка вложения, разные форматы и остальные методы требуют дополнительной проверки на сервере.

## Отдельный тестовый бот

[examples/test_bot.py](../examples/test_bot.py) — интерактивный бот для тестового аккаунта. Он читает все входящие сообщения, но выполняет команды только пользователя с `ITD_TESTER_ID`. `/help` показывает команды, в том числе `/file`, `/download FILE_ID` и `/api METHOD /api/путь [JSON]`. `/api` может выполнять операции изменения данных от имени аккаунта бота; назначайте доступ только доверенному тестировщику и используйте тестовый аккаунт.

В PowerShell после установки SDK:

```powershell
$env:ITD_TOKEN = "ВАШ_ТОКЕН_БЕЗ_BEARER"
$env:ITD_SELF_USER_ID = "ID_АККАУНТА_БОТА"
$env:ITD_TESTER_ID = "ID_ТЕСТИРОВЩИКА"
python examples/test_bot.py
```

Идентификаторы можно получить из `get_chats()` или данных чата (`other_user_id` для личного чата). Для первого запуска бот берёт текущий `event_seq` и не обрабатывает старые события; затем сохраняет курсор в `.itd-test-bot-cursor`. Для другого аккаунта задайте отдельный `ITD_CURSOR_FILE`. Обработка после сбоя может повториться; примеры не обеспечивают exactly-once. Остановка — Ctrl+C. Токен истекает; при 401 требуется новый.
