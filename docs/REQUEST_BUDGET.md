# Как сократить расход запросов

Если бот отвечает на несколько сообщений из одного пакета, включите пакетную отметку прочтения:

```python
router = Dispatcher.from_bot(bot, read_mode="batch")
router.run_polling(state_path=".bot-state.json", interval=5.0)
```

`batch` отправляет одну отметку на чат за полученный пакет, перед первым обработчиком этого чата. Вызов ждёт HTTP-ответа; другие чаты с `workers > 1` могут работать параллельно. Работает и с `chat_queues=True`: каждый пакет сохраняет собственные цели прочтения, даже если следующий уже получен.

> **Хорошо знать.** Последнее входящее сообщение чата в пакете будет отмечено до обработки более ранних. Если более поздний обработчик упадёт, отметка уже останется на сервере. Используйте `blocking`, если важна отдельная отметка перед каждым обработчиком.

## Настройки под задачу

| Задача | interval | read_mode | Условие |
|---|---:|---|---|
| Редкие сообщения, последовательная обработка | 5 с | blocking | Отдельная отметка перед каждым обработчиком |
| Быстрые ответы без ожидания прочтения | 5 с + websocket=True | background | Ошибки прочтения только логируются |
| Несколько сообщений на чат в пакете | 5 с; WebSocket по необходимости | batch | Отметка последнего сообщения до первого обработчика |
| Архивирование без отметок прочтения | 5 с | off | Бот не отмечает сообщения прочитанными |

Это рекомендации, а не новые значения по умолчанию. По умолчанию остаются `interval=2.0`, `read_mode="blocking"`, `workers=1` и защитный бюджет 80 запросов в минуту на экземпляр лимитера. Это локальная защита SDK, не подтверждённая квота ИТД. Полные правила — в [лимитах](RATE_LIMITS.md).

При простое интервал 2 секунды даёт до 30 GET в минуту, 5 секунд — до 12. Непустые пакеты с новым курсором читаются подряд: `interval` не задерживает каждый ответ. С WebSocket он задаёт запасной опрос; `min_fetch_interval=0.2` ограничивает частоту GET после сигналов. Установите extra `[websocket]` для этого режима.

SDK уже объединяет сигналы WebSocket через один флаг пробуждения и читает `/updates` одним потоком. Новые кадры во время GET не запускают параллельные запросы и объединяются в одно ожидающее пробуждение. Это проверено регрессионными тестами для обоих режимов очередей; новых повторов записи нет.

## Если отметка не удалась

В `batch` обработчики этого чата ждут успешной отметки. Обновление сессии после 401 работает по прежним правилам и сохраняет цель прочтения. Временные сбои и 429 запускают существующее повторное чтение событий с безопасного курсора; дедупликация пропускает уже успешные сообщения. Остальные ошибки поступают в `on_error`. При ручном `handle()` исключение возвращается вызывающему коду без нового повтора записи.

В `background` обработчик продолжает работу независимо от результата отметки. В `off` запросов прочтения нет. При ручном `handle()` закрывайте диспетчер, чтобы дождаться фоновых отметок.

## Измерение

Стенд, условия и результаты до/после — в [производительности](PERFORMANCE.md). Проверка использует MockTransport и подставное время; живые квоты и задержки сети не измерялись. Пример настроек: [`examples/batch_reads.py`](../examples/batch_reads.py).
