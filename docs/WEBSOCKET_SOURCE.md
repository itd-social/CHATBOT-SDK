# События из WebSocket

Включите `source="websocket"`, чтобы получать события прямо из кадров WebSocket. SDK использует HTTP для начальной сверки, восстановления пропусков и работы во время обрыва соединения.

```sh
python -m pip install "itd-chatbot-sdk[websocket]"
```

```python
from itd_bot import Bot, MessageContext, Router

with Bot.from_env() as bot:
    router = Router.from_bot(bot, **bot.dispatcher_options)

    @router.message()
    def received(ctx: MessageContext) -> None:
        ctx.reply("Сообщение получено")

    polling = {**bot.poll_options, "source": "websocket"}
    router.run_polling(state_path=".bot-state.json", **polling)
```

Настройте [окружение](ENVIRONMENT.md) перед запуском. Пример приёма сообщений, `presence` и `typing` без ответов и вывода личных данных: [`examples/websocket_source`](../examples/websocket_source/README.md).

## Выберите режим

| Настройка | Откуда приходят данные |
|---|---|
| `source="poll"` (по умолчанию) | `GET /updates`, как раньше |
| `source="poll", websocket=True` | Тот же HTTP-опрос; WebSocket только будит цикл |
| `source="websocket"` | Кадры WebSocket и HTTP для сверки и восстановления |

`source` также передаётся через `Dispatcher.run_polling` и `Router.run_polling`. При `source="websocket"` не нужно отдельно включать `websocket=True`; сочетание опций не создаёт второго соединения.

Без extra `[websocket]` явный выбор WebSocket даёт понятную ошибку установки. Обрыв или ошибка соединения WS после запуска включают HTTP-восстановление. Переподключения используют паузы от 1 до 30 секунд. Коды 4001/4003 обрабатываются прежним механизмом: доступная refresh-сессия обновляется с ограничением числа попыток на соединение.

## Курсор и пропуски

После установки соединения SDK сверяет курсор через `/updates`: так данные, появившиеся во время подключения, не зависят от момента начала чтения кадров. Начальная сверка может потребовать несколько HTTP-запросов.

Для кадра с `event_seq` ожидается шаг на `event_seq_count` (по умолчанию 1). Старые и повторные номера пропускаются. При разрыве последовательности SDK запрашивает `/updates` с текущего курсора, а ожидающий кадр сверяет с полученным результатом. Частично перекрывающийся диапазон тоже восстанавливается через HTTP; SDK не разрезает пакет сообщений сам.

Некорректные номера и входящие сообщения без номера передаются на восстановление через HTTP. Неизвестные поля корректного кадра сохраняются в исходном JSON. Для HTTP явно используется `capabilities=chat_settings`, для WS — `chat_settings_v2`.

Курсор подтверждается только после обработки согласно [политике ошибок](USAGE.md#если-обработчик-упал) и успешного вызова `on_checkpoint`. При временном сбое отметки прочтения SDK восстанавливает обработку с подтверждённого курсора; ещё не подтверждённые кадры с номерами удерживаются для повторной доставки, если HTTP отстаёт. `ResetRequired` не скрывается и останавливает цикл.

> **Осторожно.** `ErrorAction.RETRY` по-прежнему может повторить действия обработчика. Номер события и восстановление чтения не подтверждают идемпотентность отправки. Новых автоматических повторов HTTP-записи нет.

## Presence и typing

Кадр без `event_seq`, например уведомление о присутствии или наборе текста, передаётся обработчику без продвижения курсора. Если включены [очереди по чатам](CHAT_QUEUES.md), такое уведомление сохраняет порядок своего чата и задерживает подтверждение более позднего события до своего завершения. SDK не добавляет вымышленные номера в исходные словари.

Уведомления без номера не имеют гарантии восстановления после обрыва, остановки или перезапуска. Они не входят в подтверждённую последовательность журнала.

Получение этих уведомлений в режиме `poll` не обещается. Живой пункт #31 выполнен частично: результаты сравнения WS и `/updates` приведены [ниже](#что-проверено).

## Нагрузка и остановка

`min_fetch_interval` ограничивает HTTP-сверки; прямые кадры этим интервалом не задерживаются. При потере WS цикл продолжает HTTP-опрос с прежними паузами и правилами обработки 429, сетевых сбоев и 5xx.

Буфер кадров ограничен `max(2, workers) * chat_queue_size`, включая режим без очередей по чатам. Дополнительную память занимают текущий кадр, ещё не подтверждённые события, очереди обработки и текущий ответ HTTP. Если обработчики не успевают, приём ждёт освобождения места; уведомления не выбрасываются ради освобождения локального буфера.

`stop` завершает уже полученный пакет и задачи очередей. Затем закрывается источник WS; активное подключение или HTTP-обновление сессии дожидается своего таймаута. Ещё не переданные обработчикам уведомления без номера могут потеряться при остановке. Учтите это при проектировании бота.

## Что проверено

Формат проверен статически в предоставленном `index-1f7c8b01465d.js`: `aA` разбирает JSON, `D_` проверяет необязательные `event_seq` и `event_seq_count`, `A$` сравнивает шаг последовательности. Номера — неотрицательные безопасные целые JavaScript; исходный объект возвращается без переименования полей.

Автономные тесты используют `httpx.MockTransport` и подставные WebSocket: проверяются пропуски, диапазоны, повторы, переподключение, 4001/4003 с обновлением сессии, 429, сетевые сбои, очереди, прочтение и остановка. Это не проверка живого сервера.

28 ноября 2026 года в четырёхминутной проверке получены 9 кадров `presence` из WS; все дошли до обработчика нового режима. В 106 успешных ответах `/updates` за то же время `presence` не было. `typing` не получен ни из одного источника, поэтому его сравнение остаётся открытым. Эти наблюдения относятся к одному сценарию и не гарантируют поведение сервера в других условиях.
