# Лимиты запросов

ИТД может ответить 429, если запросов слишком много. Чтобы бот до этого не доходил, SDK заранее сам притормаживает. Включено по умолчанию, настраивать ничего не нужно.

> **Важно.** Числа ниже — защитные настройки SDK, подобранные с запасом по нашим испытаниям. Это **не** официальные квоты ИТД, и 429 они полностью не исключают.

## Что делает SDK

| Что | Правило по умолчанию |
|---|---|
| Все запросы вместе | Не больше 80 за 60 секунд |
| Отправка и пересылка в чат | 1 сообщение за 2,1 с, всплеск до 4 подряд |
| Отправка по ID пользователя | То же, но корзина отдельная |
| Реакции | 1 за 1,1 с, всплеск до 12 |
| Редактирование | 1 за 6,2 с, всплеск до 4 |
| Удаление «для себя» | 1 за 3,2 с, всплеск до 8 |

Как это ощущается: четыре сообщения подряд уходят сразу, пятое ждёт около 2,1 секунды, дальше по одному за 2,1 секунды. После паузы «корзина» снова наполняется.

Что полезно знать:

- Корзины ведутся отдельно для каждой пары (аккаунт, чат). Если лимит поймали в одном чате, в другом бот пишет спокойно.
- Пересылка трёх сообщений тратит три «токена», а удаление для себя всегда один, сколько бы ID вы ни передали.
- Удаление «для всех» этим правилам не подчиняется: 100 удалений за 31 секунду прошли без 429.
- Ограничения считают всё: polling, отметки прочтения, typing, загрузки, refresh и повтор после 401. Даже неудачный запрос тратит бюджет.
- Боты в одном процессе с одним адресом сервера делят общий лимитер. Разные процессы друг о друге не знают.

> **Бот много общается?** Увеличьте `interval` опроса или включите [WebSocket](USAGE.md#быстрые-обновления-и-параллельная-работа): так обновления перестанут съедать общий бюджет.

## Настройка

```python
import os
from itd_bot import Bot, RateLimitConfig, RateLimiter

limiter = RateLimiter(RateLimitConfig(
    requests_per_minute=40,
    send_interval=2.5,
    reaction_interval=1.5,
    edit_interval=7.0,
))

with Bot.from_refresh_token(os.environ["ITD_REFRESH_TOKEN"], limiter=limiter) as bot:
    print(bot.get_me().username)
```

Параметры, которые могут пригодиться:

| Параметр | Что делает |
|---|---|
| `requests_per_minute` | Общий бюджет. `None` отключает его |
| `min_interval` | Пауза между любыми запросами (по умолчанию 0) |
| `send_interval`, `reaction_interval`, `edit_interval`, `delete_for_me_interval` | Время восстановления одного токена |
| `send_burst`, `reaction_burst`, `edit_burst`, `delete_for_me_burst` | Размер корзины (целое от 1) |
| `wait=False` | Не ждать, а сразу бросать `RateLimitError` с `locally_blocked=True` |
| `enabled=False` | Выключить заранее заданные паузы. Ответы 429 по-прежнему учитываются |

Хотите, чтобы несколько ботов делили лимиты? Передайте им один и тот же `limiter`. Это особенно важно для ботов на одном IP.

## Если пришёл 429

SDK не повторяет запрос сам, а бросает `RateLimitError`. Следующий вызов подождёт, пока не пройдёт пауза, которую назвал сервер (`Retry-After`).

```python
from itd_bot import RateLimitError

try:
    bot.send_message("CHAT_ID", "Привет")
except RateLimitError as error:
    print(error.code, error.retry_after_seconds)
```

Что происходит под капотом:

- Блокируется только та группа, из которой пришёл 429: тот же чат и тот же аккаунт. Другие чаты не страдают.
- Если сервер не назвал время, SDK подождёт 2 секунды (отправка) или 30 секунд (всё остальное).
- Ответы `ip_flood` и `global_flood` останавливают все запросы лимитера.
- `new_recipients_hour` и `new_recipients_day` касаются новых собеседников: пауза действует только для запроса, который получил ошибку. SDK не знает, кого сервер считает новым.

Повторять ли отправку после сетевого сбоя, решает ваш код: мы не знаем точно, дошло ли сообщение.

## Лимит загрузок

Если закончился бюджет на загрузки, приходит `UploadQuotaError` (она не `RateLimitError`) без автоматического повтора.

```python
from itd_bot import UploadQuotaError

try:
    bot.send_file("CHAT_ID", "report.pdf")
except UploadQuotaError as error:
    print(error.code)
```

Сначала разберитесь с незавершёнными загрузками, потом начинайте новые. Размер бюджета и срок очистки неизвестны, а `Retry-After` тут не гарантирует освобождение. В своих загрузчиках сохраняйте `uploadId` сразу после ответа init.

## Что мы проверяли

Все цифры выше получены из опытов, а не из спецификации сервера.

- **Отправка и пересылка** делят одну корзину в чате. После 429 в чате A отправка в чат B проходила (12 из 12 проб). Независимость между аккаунтами проверена только для отправки.
- **Правки, реакции и удаление для себя** тоже независимы между чатами (по 3 из 3). Между аккаунтами это проверено лишь автотестами.
- **Всплески до 429:** отправка и правка около 5 подряд, удаление для себя 10–11, реакции 21–24 в плотной серии. Значения в SDK выбраны с запасом ниже.
- **Загрузки:** после серии незавершённых init пришёл `UPLOAD_QUOTA_EXCEEDED`, а 25 полных загрузок подряд прошли.
- **Остальные маршруты** (непрочитанные, медиа, присутствие, каталог реакций, typing, pin, mute, unread, файловые ссылки и скачивание) выдержали серии по 75 запросов без 429. Это нижняя граница, а не точная квота.
- Не проверены: большие пакеты пересылки, создание личных чатов, принятие запросов. Удаление чата и очистка истории из исследования исключены.

## Для тех, кто пишет свой лимитер

Лимитер вызывается так: `RateLimiter.acquire(method, path, *, cost=1, account=None)` и `observe(response, method, path, account=None)`. Ключ аккаунта берётся из `sub` токена (хешируется, не попадает в логи), а если его нет, случайный на каждый `Bot`. Бот с одним `sub` делит корзины, с разным не делит. Корзины хранятся в памяти (до 4096 штук), и полностью восстановленные удаляются.
