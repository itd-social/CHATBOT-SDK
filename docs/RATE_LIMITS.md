# Ограничения запросов

Защита включена при обычном создании `Bot` и через `Bot.from_refresh_token`. Перед сетевым запросом SDK ждёт свободное место в общем бюджете и, для сообщений, выдерживает паузу соответствующей группы.

| Правило по умолчанию | Значение |
|---|---|
| Все запросы | До 80 за последние 60 секунд |
| Общая задержка между запросами | Отсутствует (`min_interval=0`) |
| Отправка и пересылка в чат | Корзина на пару (аккаунт, чат): восстановление 2,1 секунды на токен, корзина 4 |
| Отправка по ID пользователя | Отдельная корзина на (аккаунт, пользователь), те же 2,1 секунды и 4 |
| Изменение реакций | Корзина на (аккаунт, чат): восстановление 1,1 секунды, корзина 12 |
| Редактирование сообщений | Корзина на (аккаунт, чат): восстановление 6,2 секунды, корзина 4 |
| Удаление сообщений только для себя | Корзина на (аккаунт, чат): восстановление 3,2 секунды, корзина 8 |

Это защитные настройки клиента, выбранные по результатам испытаний с запасом. Они не являются официальными квотами ИТД и не гарантируют отсутствие 429. Независимые запросы не задерживаются, пока не исчерпан общий бюджет. Действуют отдельные интервалы сообщений. Общий бюджет является предохранителем от блокировки IP, а не общей серверной квотой всех маршрутов. Группы сообщений работают как корзина токенов (см. ниже), а не как фиксированная пауза. Для пересылки учитывается число `message_ids`: пакет из трёх сообщений списывает три токена. Общий бюджет HTTP учитывает такой пакет как один запрос. Пакет не разбивается автоматически: большой пакет сам может превысить серверный допустимый всплеск, поэтому для него нельзя гарантировать отсутствие 429. В живых опытах проверены пакеты из двух и трёх сообщений.

Удаление для себя имеет отдельную корзину: после исчерпания квоты в повторных опытах восстанавливалась примерно одна операция за 3 секунды. Пакет из трёх ID после паузы был принят целиком, поэтому для него списывается один токен. Удаление для всех не использует это правило: 100 отдельных реальных удалений за 31.24 секунды прошли без 429. Это границы проведённых опытов, а не полная серверная спецификация.

## Корзина токенов

Для групп отправки, редактирования, реакций и удаления для себя SDK использует корзину токенов (алгоритм GCRA). Поля `*_interval` задают период восстановления одного токена, поля `*_burst` — размер корзины, то есть число операций подряд без ожидания после простоя. Один запрос списывает `cost` токенов: для обычных операций 1, для пересылки число `message_ids`.

| Поле | По умолчанию | Наблюдалось до первого 429 |
|---|---|---|
| `send_burst` | 4 | 5 успехов подряд |
| `edit_burst` | 4 | 5 успехов подряд |
| `reaction_burst` | 12 | 21-24 успеха в плотной серии при примерно 1 с на токен; оценка ёмкости около 15 |
| `delete_for_me_burst` | 8 | 10-11 успехов подряд |

Значения `*_burst` выбраны с запасом ниже наблюдавшихся и не являются опубликованной конфигурацией сервера. Для реакций число успехов в плотной серии включает токены, восстановившиеся за время самой серии, поэтому запас считается от оценки ёмкости около 15, а не от 21-24. Каждое поле — целое число не меньше 1; `burst=1` даёт прежнее поведение с фиксированной паузой между операциями группы.

С настройками по умолчанию четыре отправки подряд проходят без ожидания, пятая ждёт около 2,1 секунды, далее по одной за 2,1 секунды. После простоя в 4 * 2,1 секунды корзина снова полна; после простоя в один интервал доступен один токен.

Если `cost` больше `burst`, SDK ждёт полной корзины, затем списывает все токены сразу, и корзина уходит в долг на будущее: следующие операции группы ждут, пока долг не погасится. Запрос не зависает и не разбивается. Для больших пакетов это не проверено живыми опытами: сервер всё равно может ответить 429.

При 429 по группе пустой считается только та корзина, из которой пришёл ответ (аккаунт и чат из пути запроса), на момент ответа. Следующий допуск в ней не раньше времени, названного сервером, затем по одному токену за интервал, без нового всплеска. Корзины других чатов, других аккаунтов и других групп не затрагиваются.

## Область корзин

Корзины ведутся отдельно для каждого аккаунта и внутри аккаунта по ключам из таблицы; для отправки в чат, реакций, правок и удаления для себя ключ включает ID чата из пути `/chats/{id}/...`. Параметры `*_interval` и `*_burst` и логика корзины от области не зависят.

| Группа | Ключ корзины | Что наблюдалось |
|---|---|---|
| Отправка и пересылка в чат | (аккаунт, чат); пересылка в чат C расходует ту же корзину, что и отправка в C | Независимость между чатами проверена: после 429 бота в чате A отправка в чат B проходила (12 из 12 проб по чатам и аккаунтам). Независимость между аккаунтами проверена только для отправки. В 429 отправки заголовок `X-RateLimit-Scope: chat`. |
| Отправка пользователю (`POST /users/{id}/messages`) | (аккаунт, «user», ID пользователя) | Соотношение с корзиной чата того же личного диалога не проверено; SDK считает их разными корзинами. |
| Реакции | (аккаунт, чат) | В 429 заголовок `X-RateLimit-Scope: chat`. После 429 бота в чате A реакция в чате B проходила сразу (3 из 3). Между аккаунтами не проверялась. |
| Редактирование | (аккаунт, чат) | После 429 бота в чате A правка в чате B проходила сразу (3 из 3, запрос уходил раньше срока Retry-After). 429 приходит без `X-RateLimit-Scope` и без `X-RateLimit-Retry-After-Ms` (только целый `Retry-After` и текст ошибки). Между аккаунтами не проверялась. |
| Удаление для себя | (аккаунт, чат) | То же: после 429 в чате A удаление в чате B проходило сразу (3 из 3). Заголовков scope и миллисекунд нет. Между аккаунтами не проверялось. |

Общими для всех аккаунтов и чатов одного ограничителя остаются общий бюджет запросов (по умолчанию 80 за 60 секунд) и cooldown `ip_flood` и `global_flood`: предохранитель IP общий по IP, а не по аккаунту. Cooldown `new_recipients_hour` и `new_recipients_day` работают как раньше. Живая приёмка с настройками по умолчанию проведена с одним аккаунтом и одним чатом (без 429). Независимость между аккаунтами наблюдалась только для отправки; для остальных групп разделение по аккаунтам проверено лишь автономными тестами с подменой времени и транспорта.

### Идентификатор аккаунта

`Bot` передаёт ограничителю ключ аккаунта в `acquire(..., account=...)` и `observe(..., account=...)`. Источник ключа по порядку:

1. Идентификатор пользователя (`sub`) из access-токена или из сохранённой сессии. SDK не запрашивает профиль ради этого, а подпись JWT не проверяется: ключ нужен только для разделения локальных корзин.
2. Если `sub` нет, случайный ключ, уникальный для экземпляра `Bot`.

Токен и `sub` в ключ целиком не попадают, используется усечённый SHA-256. Ключ не меняется при обновлении токена: refresh и повторный запрос после 401 сохраняют аккаунт. Идентификаторы чатов и аккаунтов не выводятся в логи и в `RateLimitError`.

Боты с одним `sub` и общим ограничителем делят корзины, с разным `sub` не делят. Токены без `sub` считаются разными аккаунтами у каждого `Bot`, даже если на сервере это один аккаунт: такие боты не объединят корзины друг с другом.

`RateLimiter.acquire(method, path, *, cost=1, account=None)` и `observe(response, method, path, account=None)` можно вызывать и напрямую. `account=None` означает один общий аккаунт; чаты при этом всё равно получают отдельные корзины. Собственный подкласс с прежней сигнатурой этих методов нужно обновить.

### Память

Корзина, полностью восстановившаяся до заполнения, равносильна отсутствующей и удаляется при обращении к ограничителю, не чаще раза в 5 секунд. Число хранимых корзин ограничено (4096): при превышении удаляются корзины с наименьшим долгом, то есть ближайшие к восстановлению, и такой чат получит полный всплеск раньше, чем следовало бы.

## Что учитывается

Через ограничитель проходят обычные и экспериментальные API-вызовы, polling, отметки прочтения, typing, реакции, init/части/finalize загрузок, файловые сессии, скачивание файлов и баннеров, refresh и повторный HTTP-запрос после 401. Установка WebSocket-соединения тоже учитывается; ping и кадры уже открытого соединения не считаются отдельными HTTP-запросами.

Неудачный HTTP-запрос или попытка с сетевой ошибкой тоже расходуют локальный бюджет. Ожидание может увеличить задержку ответа и отложить typing. Частый polling расходует тот же бюджет, поэтому для бота с активной перепиской разумно увеличить интервал опроса или использовать WebSocket как сигнал обновления.

По умолчанию все `Bot` с одинаковой строкой origin делят один ограничитель в текущем процессе. Корзины отправки, реакций, редактирования и удаления для себя ведутся по паре (аккаунт, чат), отправки пользователю по (аккаунт, пользователь) (см. «Область корзин»); общий бюджет запросов и cooldown по IP общие для всех. Разные процессы, разные origin и другие приложения с того же IP не координируются. Закрытие одного бота не сбрасывает общий бюджет остальных.

## Настройка

```python
import os
from itd_bot import Bot, RateLimitConfig, RateLimiter

limiter = RateLimiter(RateLimitConfig(
    requests_per_minute=40,
    min_interval=1.5,
    send_interval=2.5,
    reaction_interval=1.5,
    edit_interval=7.0,
))

with Bot.from_refresh_token(
    os.environ["ITD_REFRESH_TOKEN"], limiter=limiter
) as bot:
    print(bot.get_me().username)
```

Переданный вручную ограничитель не объединяется с ограничителями других клиентов автоматически. Для нескольких ботов передавайте им один и тот же объект `limiter`. Это особенно важно для ботов на одном IP.

`RateLimitConfig(requests_per_minute=None)` отключает только общий минутный бюджет, сохраняя отдельные правила сообщений и серверные cooldown. Используйте это при собственной координации общей нагрузки. `min_interval` по умолчанию равен нулю; его можно явно увеличить, если требуется равномерная отправка всех запросов.

`RateLimitConfig(wait=False)` включает неблокирующий режим: вместо ожидания SDK выбрасывает `RateLimitError` с `locally_blocked=True` и `retry_after_seconds`. Такой вызов не отправляется на сервер и не расходует новое место в очереди.

`RateLimitConfig(enabled=False)` отключает предварительные интервалы и общий бюджет, но сохраняет обработку уже полученных серверных cooldown. Для внешнего планировщика можно совместить `enabled=False, wait=False`. Числа интервалов должны быть конечными и неотрицательными, `requests_per_minute` должен быть положительным целым числом или `None`.

## Ответ 429

SDK читает `Retry-After` в секундах или формате HTTP-даты, а также `X-RateLimit-Retry-After-Ms`, и сохраняет более длительное ожидание. Для групп сообщений дробное значение из `X-RateLimit-Retry-After-Ms` не округляется вверх, если целочисленное значение в `Retry-After` или в теле ответа не длиннее него: ответ с 54 мс означает ожидание около 0,054 секунды, а не секунды. Для остальных маршрутов и для `ip_flood` и `global_flood` ожидание округляется вверх, как раньше. `RateLimitError.retry_after_seconds` остаётся целым числом. Также учитываются `error.retryAfter` и `error.retry_after` из тела ответа. Если сервер не сообщил корректное время, применяется запасная пауза: 2 секунды для отправки по чату/пользователю, 30 секунд для остальных запросов.

Остальные известные HTTP-маршруты имеют раздельные cooldown по методу и шаблону пути: смена ID сообщения, файла или части загрузки не обходит паузу этого маршрута. Пауза другого маршрута при этом не добавляется. Для неизвестных экспериментальных путей используется точный метод и путь. Это не означает знания численных серверных квот.

При 429 отправки cooldown распространяется на пересылку в тот же чат того же аккаунта; другие чаты, другие аккаунты и отправка пользователю не блокируются. Для редактирования, удаления для себя и реакций он распространяется на другие ID сообщений того же чата того же аккаунта; другие чаты и аккаунты не блокируются. `ip_flood` и `global_flood` блокируют все маршруты данного ограничителя. Новое короткое ожидание не сокращает уже действующую более длинную паузу.

Ограничения `new_recipients_hour` и `new_recipients_day` относятся к новым собеседникам: в бандле прямо указано, что писать прежним можно. Такой ответ сохраняет cooldown только для точного метода и пути, вернувшего ошибку, и не замораживает общую группу отправки. SDK не определяет самостоятельно, кого сервер считает новым собеседником; другая попытка первого контакта тоже может получить 429. Числа этих квот и их периоды восстановления не измерены. Само название scope не означает обязательного ожидания ровно часа или суток; используется переданный сервером Retry-After.

Запрос, получивший 429, выбрасывает `RateLimitError`; SDK не повторяет его автоматически. Следующий вызов дождётся окончания cooldown, если включён `wait`. Уже отправленные конкурентные запросы отозвать нельзя.

```python
from itd_bot import RateLimitError

try:
    bot.send_message("CHAT_ID", "Привет")
except RateLimitError as error:
    print(error.code, error.retry_after_seconds)
```

Результат сетевого сбоя записи может быть неизвестен. Повтор сообщения после ошибки остаётся решением приложения; точно установленных гарантий идемпотентности нет. Polling повторяет только получение событий, а не обработчик уже полученного сообщения.

## Бюджет загрузок

`429/UPLOAD_QUOTA_EXCEEDED` преобразуется в отдельную `UploadQuotaError`, наследующую `APIError`, а не `RateLimitError`. Она содержит `code` и исходный `retry_after`. Эта ошибка не запускает автоматический повтор и не трактуется как обычное истечение минутной квоты.

```python
from itd_bot import UploadQuotaError

try:
    bot.send_file("CHAT_ID", "report.pdf")
except UploadQuotaError as error:
    print(error.code)
```

Нужно разобраться с бюджетом и незавершёнными загрузками, прежде чем создавать новые init. Точный размер бюджета и срок очистки не установлены. Обычный `upload_file` выполняет init, части и finalize последовательно; он не предоставляет гарантированного серверного отката при обрыве процесса. В экспериментальных загрузчиках сохраняйте `uploadId` сразу после ответа init, до следующих запросов.


## Что подтверждено испытаниями

Числа защитных интервалов и размеров корзин выше выбраны с запасом по наблюдаемому восстановлению квот. Это не опубликованная конфигурация сервера.

| Операция | Результат проверки | Что учитывает SDK |
|---|---|---|
| Отправка и пересылка | В одном чате расходуют общую квоту. Пересылка двух и трёх сообщений расходовала соответствующее число отправок. После 429 бота в чате A отправка в чат B проходила (12 из 12 проб по чатам и аккаунтам); в 429 заголовок `X-RateLimit-Scope: chat`. | Корзина на (аккаунт, чат); вес пересылки равен числу ID. |
| Редактирование | После 429 одного сообщения редактирование другого ID того же чата тоже получало 429; отправка и реакции оставались доступны. После 429 в чате A правка в чате B проходила сразу (3 из 3). 429 без scope и без `X-RateLimit-Retry-After-Ms`. | Отдельная корзина редактирования на (аккаунт, чат). |
| Реакции | Получен собственный 429 с `X-RateLimit-Scope: chat`; после него отправка и редактирование оставались доступны. После 429 в чате A реакция в чате B проходила сразу (3 из 3). | Отдельная корзина реакций на (аккаунт, чат). |
| Удаление для себя | После 10-11 быстрых успешных запросов получен 429; в следующих трёх циклах восстанавливалась одна операция примерно за 3 секунды. Пакет из трёх ID прошёл после одной паузы. После 429 в чате A удаление в чате B проходило сразу (3 из 3). | Отдельная корзина на (аккаунт, чат), один токен на запрос с восстановлением 3,2 секунды, независимо от числа ID. |
| Загрузки | После серии незавершённых init получен UPLOAD_QUOTA_EXCEEDED. Отдельно прошли 25 последовательных полных загрузок, все завершены. | Отдельная ошибка ресурсного бюджета; Retry-After не считается гарантией его освобождения. |

Для 11 других маршрутов прошли серии по 75 запросов без 429: получение непрочитанного, медиа, присутствия одним и несколькими ID, каталога и списка реакций, сообщений вокруг ID, typing, а также изменение pin, mute и unread с восстановлением состояния. Для файловых ссылок, файловой cookie и скачивания также прошли по 75 запросов; скачанные байты проверены. Исследовательская нагрузка ограничивалась 80 началами запросов за 60 секунд и одним соединением. Эти успешные серии дают нижнюю границу испытаний, а не точные квоты маршрутов; такой предел не добавлен как индивидуальное правило SDK.

Повторные отметки прочтения и прослушивания одного сообщения могут ничего не менять после первого вызова. POST `/chats/{chat}/heard` получает статусы прослушивания, а POST `/chats/{chat}/messages/{message}/heard` отмечает прослушивание. Их нельзя считать одной операцией.
