# Ограничения запросов

Защита включена при обычном создании `Bot` и через `Bot.from_refresh_token`. Перед сетевым запросом SDK ждёт свободное место в общем бюджете и, для сообщений, выдерживает паузу соответствующей группы.

| Правило по умолчанию | Значение |
|---|---|
| Все запросы | До 50 за последние 60 секунд |
| Общая задержка между запросами | Отсутствует (`min_interval=0`) |
| Отправка, пересылка, отправка по ID пользователя | Одна общая группа, интервал 2,1 секунды |
| Изменение реакций | Интервал 1,1 секунды |
| Редактирование сообщений | Интервал 6,2 секунды |
| Удаление сообщений только для себя | Интервал 3,2 секунды на запрос |

Это защитные настройки клиента, выбранные по результатам испытаний с запасом. Они не являются официальными квотами ИТД и не гарантируют отсутствие 429. Независимые запросы не задерживаются, пока не исчерпан общий бюджет. Действуют отдельные интервалы сообщений. Общий бюджет является предохранителем от блокировки IP, а не общей серверной квотой всех маршрутов. Начального всплеска отдельных запросов нет. Для пересылки учитывается число `message_ids`: после пакета из трёх сообщений группа отправки освобождается через 3 * 2,1 секунды. Общий бюджет HTTP учитывает такой пакет как один запрос. Пакет не разбивается автоматически: большой пакет сам может превысить серверный допустимый всплеск, поэтому для него нельзя гарантировать отсутствие 429. В живых опытах проверены пакеты из двух и трёх сообщений.

Удаление для себя имеет отдельный интервал: после исчерпания квоты в повторных опытах восстанавливалась примерно одна операция за 3 секунды. Пакет из трёх ID после паузы был принят целиком, поэтому для него учитывается один запрос. Удаление для всех не использует это правило: 100 отдельных реальных удалений за 31.24 секунды прошли без 429. Это границы проведённых опытов, а не полная серверная спецификация.

## Что учитывается

Через ограничитель проходят обычные и экспериментальные API-вызовы, polling, отметки прочтения, typing, реакции, init/части/finalize загрузок, файловые сессии, скачивание файлов и баннеров, refresh и повторный HTTP-запрос после 401. Установка WebSocket-соединения тоже учитывается; ping и кадры уже открытого соединения не считаются отдельными HTTP-запросами.

Неудачный HTTP-запрос или попытка с сетевой ошибкой тоже расходуют локальный бюджет. Ожидание может увеличить задержку ответа и отложить typing. Частый polling расходует тот же бюджет, поэтому для бота с активной перепиской разумно увеличить интервал опроса или использовать WebSocket как сигнал обновления.

По умолчанию все `Bot` с одинаковой строкой origin делят один ограничитель в текущем процессе. Группы отправки, реакций, редактирования и удаления для себя консервативно общие для всех чатов и аккаунтов этого ограничителя: независимость серверных счётчиков между чатами ещё не установлена. Разные процессы, разные origin и другие приложения с того же IP не координируются. Закрытие одного бота не сбрасывает общий бюджет остальных.

## Настройка

```python
import os
from itd_bot import Bot, RateLimitConfig, RateLimiter

limiter = RateLimiter(RateLimitConfig(
    requests_per_minute=40,
    min_interval=1.5,
    send_interval=2.5,
    reaction_interval=1.5,
    edit_interval=7.0,
))

with Bot.from_refresh_token(
    os.environ["ITD_REFRESH_TOKEN"], limiter=limiter
) as bot:
    print(bot.get_me().username)
```

Переданный вручную ограничитель не объединяется с ограничителями других клиентов автоматически. Для нескольких ботов передавайте им один и тот же объект `limiter`. Это особенно важно для ботов на одном IP.

`RateLimitConfig(requests_per_minute=None)` отключает только общий минутный бюджет, сохраняя отдельные правила сообщений и серверные cooldown. Используйте это при собственной координации общей нагрузки. `min_interval` по умолчанию равен нулю; его можно явно увеличить, если требуется равномерная отправка всех запросов.

`RateLimitConfig(wait=False)` включает неблокирующий режим: вместо ожидания SDK выбрасывает `RateLimitError` с `locally_blocked=True` и `retry_after_seconds`. Такой вызов не отправляется на сервер и не расходует новое место в очереди.

`RateLimitConfig(enabled=False)` отключает предварительные интервалы и общий бюджет, но сохраняет обработку уже полученных серверных cooldown. Для внешнего планировщика можно совместить `enabled=False, wait=False`. Числа интервалов должны быть конечными и неотрицательными, `requests_per_minute` должен быть положительным целым числом или `None`.

## Ответ 429

SDK читает `Retry-After` в секундах или формате HTTP-даты, а также `X-RateLimit-Retry-After-Ms`, и сохраняет более длительное ожидание. Также учитываются `error.retryAfter` и `error.retry_after` из тела ответа. Если сервер не сообщил корректное время, применяется запасная пауза: 2 секунды для отправки по чату/пользователю, 30 секунд для остальных запросов.

Остальные известные HTTP-маршруты имеют раздельные cooldown по методу и шаблону пути: смена ID сообщения, файла или части загрузки не обходит паузу этого маршрута. Пауза другого маршрута при этом не добавляется. Для неизвестных экспериментальных путей используется точный метод и путь. Это не означает знания численных серверных квот.

При 429 отправки cooldown распространяется также на пересылку и отправку пользователю. Для редактирования он распространяется на другие ID сообщений; для реакций используется собственная группа. `ip_flood` и `global_flood` блокируют все маршруты данного ограничителя. Новое короткое ожидание не сокращает уже действующую более длинную паузу.

Ограничения `new_recipients_hour` и `new_recipients_day` относятся к новым собеседникам: в бандле прямо указано, что писать прежним можно. Такой ответ сохраняет cooldown только для точного метода и пути, вернувшего ошибку, и не замораживает общую группу отправки. SDK не определяет самостоятельно, кого сервер считает новым собеседником; другая попытка первого контакта тоже может получить 429. Числа этих квот и их периоды восстановления не измерены. Само название scope не означает обязательного ожидания ровно часа или суток; используется переданный сервером Retry-After.

Запрос, получивший 429, выбрасывает `RateLimitError`; SDK не повторяет его автоматически. Следующий вызов дождётся окончания cooldown, если включён `wait`. Уже отправленные конкурентные запросы отозвать нельзя.

```python
from itd_bot import RateLimitError

try:
    bot.send_message("CHAT_ID", "Привет")
except RateLimitError as error:
    print(error.code, error.retry_after_seconds)
```

Результат сетевого сбоя записи может быть неизвестен. Повтор сообщения после ошибки остаётся решением приложения; точно установленных гарантий идемпотентности нет. Polling повторяет только получение событий, а не обработчик уже полученного сообщения.

## Бюджет загрузок

`429/UPLOAD_QUOTA_EXCEEDED` преобразуется в отдельную `UploadQuotaError`, наследующую `APIError`, а не `RateLimitError`. Она содержит `code` и исходный `retry_after`. Эта ошибка не запускает автоматический повтор и не трактуется как обычное истечение минутной квоты.

```python
from itd_bot import UploadQuotaError

try:
    bot.send_file("CHAT_ID", "report.pdf")
except UploadQuotaError as error:
    print(error.code)
```

Нужно разобраться с бюджетом и незавершёнными загрузками, прежде чем создавать новые init. Точный размер бюджета и срок очистки не установлены. Обычный `upload_file` выполняет init, части и finalize последовательно; он не предоставляет гарантированного серверного отката при обрыве процесса. В экспериментальных загрузчиках сохраняйте `uploadId` сразу после ответа init, до следующих запросов.


## Что подтверждено испытаниями

Числа защитных интервалов выше выбраны с запасом по наблюдаемому восстановлению квот. Это не опубликованная конфигурация сервера.

| Операция | Результат проверки | Что учитывает SDK |
|---|---|---|
| Отправка и пересылка | В одном чате расходуют общую квоту. Пересылка двух и трёх сообщений расходовала соответствующее число отправок. | Общая группа; вес пересылки равен числу ID. |
| Редактирование | После 429 одного сообщения редактирование другого ID того же чата тоже получало 429; отправка и реакции оставались доступны. | Отдельная группа редактирования. |
| Реакции | Получен собственный 429; после него отправка и редактирование оставались доступны. | Отдельная группа реакций. |
| Удаление для себя | После 11 быстрых успешных запросов получен 429; в следующих трёх циклах восстанавливалась одна операция примерно за 3 секунды. Пакет из трёх ID прошёл после одной паузы. | Отдельный интервал 3,2 секунды на запрос, независимо от числа ID. |
| Загрузки | После серии незавершённых init получен UPLOAD_QUOTA_EXCEEDED. Отдельно прошли 25 последовательных полных загрузок, все завершены. | Отдельная ошибка ресурсного бюджета; Retry-After не считается гарантией его освобождения. |

Для 11 других маршрутов прошли серии по 75 запросов без 429: получение непрочитанного, медиа, присутствия одним и несколькими ID, каталога и списка реакций, сообщений вокруг ID, typing, а также изменение pin, mute и unread с восстановлением состояния. Для файловых ссылок, файловой cookie и скачивания также прошли по 75 запросов; скачанные байты проверены. Исследовательская нагрузка ограничивалась 80 началами запросов за 60 секунд и одним соединением. Эти успешные серии дают нижнюю границу испытаний, а не точные квоты маршрутов; такой предел не добавлен как индивидуальное правило SDK.

Повторные отметки прочтения и прослушивания одного сообщения могут ничего не менять после первого вызова. POST `/chats/{chat}/heard` получает статусы прослушивания, а POST `/chats/{chat}/messages/{message}/heard` отмечает прослушивание. Их нельзя считать одной операцией. Точные лимиты создания нового личного чата и принятия настоящего входящего запроса также остаются неизвестными. Сравнение квот разных чатов и операции удаления чата/очистки истории в текущем исследовании исключены.
