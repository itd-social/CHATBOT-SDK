# Замеры производительности

Запускайте из корня репозитория после установки `.[dev]`. Живой сервер и учётные данные не нужны:

```sh
python -m pytest -m perf -q -s
python benchmarks/measure.py --label before-25 > before-25.json
```

Обычный `pytest` исключает маркер `perf`; явный `-m perf` включает его. Проверки Ruff охватывают `benchmarks/`. Зависимостей сверх `httpx` и инструментов разработки нет.

## Что измеряется

- `send_message`: полный синхронный вызов через `httpx.MockTransport`, локальные паузы отключены. Ответ создаётся заново на каждый запрос.
- `dispatcher_unique_message`: создание вымышленного события и `Dispatcher.handle` с пустым обработчиком, без typing и отметок прочтения. ID всегда новый: попадание в dedup-кэш не подменяет обработку сообщения.
- `json_decode_100_events`: только `json.loads` одной и той же страницы из 100 событий.
- `get_updates_100_events`: полный вызов `/updates` через MockTransport, включая HTTP, JSON и проверку оболочки.

По умолчанию выполняются 100 прогревочных вызовов, затем пять серий по 2000 вызовов. JSON содержит медиану, минимум и максимум в микросекундах, версию Python и httpx, платформу и SHA-256 файла клиента. Изменить длину можно через `--iterations` и `--rounds`. Абсолютные задержки зависят от машины и нагрузки; тесты не вводят для них жёсткий порог.

Отдельное сравнение с медленным чатом проверяет оба режима: старое ожидание пакета задерживает B из следующего пакета, а `chat_queues=True` позволяет B закончить до освобождения A. Порядок проверяется сигналами, без требования уложиться в микросекундный порог.

## Пропускная способность и бюджет

Сценарий `throughput` выполняет 120 ответов в четырёх чатах, пакетами по 10 событий, с `workers=1`, без typing и без WebSocket. `get_updates`, прочтение и отправка проходят через настоящий лимитер с неизменённым `RateLimitConfig()`. Ожидание лимитера двигает подставные часы, а не реальное время. Каждый обработчик отправляет ровно один ответ. События и ответы вымышлены, запросы идут только в MockTransport.

Отчёт показывает число запросов каждого вида, виртуальную длительность, число ответов строго до 60-й секунды и среднюю скорость всего конечного прогона. Последняя может превышать 80 ответов в минуту из-за начального запаса лимитера и границ окна: это не установившаяся скорость и не квота сервера. Пустого опроса в этом сценарии нет; его стоимость оценивайте отдельно для своего трафика.

## Сравнение с v1.3.1

Чтобы использовать тот же стенд со старым SDK, извлеките только исходники пакета из локального тега в игнорируемый каталог:

```sh
git archive --format=zip --output=.venv/bench-v1.3.1.zip v1.3.1 itd_bot
python -c "import zipfile; zipfile.ZipFile('.venv/bench-v1.3.1.zip').extractall('.venv/bench-v1.3.1')"
python benchmarks/measure.py --sdk-path .venv/bench-v1.3.1 --label v1.3.1 > v131.json
python benchmarks/measure.py --label current > current.json
```

Запускайте сравниваемые версии последовательно, на одной машине, с одинаковыми параметрами. `--sdk-path` должен указывать на доверенные исходники: Python загрузит их как код. Хэш в отчёте позволяет проверить, какой клиент измерялся. Состав обязательных зависимостей и код самого стенда между запусками должны совпадать.
