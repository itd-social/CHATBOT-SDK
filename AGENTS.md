# Работа с ITD ChatBot SDK

Памятка для агентов и разработчиков репозитория. Прямые просьбы пользователя важнее правил ниже. Если пользователь не программист, сами запустите доступные проверки и объясните результат простыми словами: что получилось, что нет и что нужно сделать ему.

## С чего начать

1. Прочитайте этот файл, задачу и связанные файлы. Не перезаписывайте чужие изменения и документы, которые пользователь просил не трогать.
2. Читайте по теме:
   - процесс разработки: `dev.md`;
   - ветки и коммиты: `GIT_WORKFLOW.md`;
   - выпуск и публикация: `RELEASING.md`, `docs/PUBLISHING.md`;
   - установка и первый бот: `README.md`, `docs/GETTING_STARTED.md`;
   - интерфейс: `docs/USAGE.md`, `docs/API_REFERENCE.md`;
   - сессия: `docs/AUTH.md`; лимиты: `docs/RATE_LIMITS.md`; маршруты: `docs/ROUTE_INVENTORY.md`;
   - как писать документацию: `docs/WRITING_DOCS.md`.
3. Если документация и код расходятся, верьте коду и бандлу. Ни документация, ни серверная спецификация не безошибочны.
4. Не создавайте новую копию репозитория или ветку без нужды. Перед любыми изменениями истории проверьте состояние Git.

## Как устроен проект

- `itd_bot/client.py`: синхронный клиент `Bot`, методы API, события, файлы.
- `auth.py`: обновление токена и сохранение refresh-cookie.
- `dispatcher.py`: команды и события. `formatting.py`: сущности форматирования. `errors.py`, `rate_limits.py`: ошибки и паузы.
- `examples/`: примеры. `tests/`: автономные тесты с подменой HTTP. `.github/workflows/`: CI и релизы. `pyproject.toml`: зависимости и версия.

Структура может меняться, сверяйтесь с файлами.

## Главные правила

**Не выдумывайте за сервер.** SDK построен по клиентскому бандлу ИТД и работает от имени пользовательского аккаунта. Не придумывайте маршруты, квоты, схемы, гарантии доставки и идемпотентность. Если чего-то не проверили, так и скажите.

**Берегите совместимость.** Не ломайте публичный интерфейс, исходные поля JSON и защиту от опасных путей.

**Помните об особенностях SDK:**
- обработка 401 и ротация сессии;
- блокировки после 429;
- потоковая загрузка файлов;
- UTF-16 в форматировании;
- отметка прочтения до обработчика и typing;
- повторная доставка событий: курсор сохраняется только после успешной обработки пакета;
- `ResetRequired` нельзя скрывать.

**Не повторяйте запись вслепую.** Сетевая ошибка не говорит, выполнилась ли запись. Пока сервер не подтвердил идемпотентность, автоповторов быть не должно. Пауза после 429 не означает, что мы знаем реальные квоты. Разные процессы не координируют ни локальные лимиты, ни refresh-сессию.

**Пишите просто.** Понятный типизированный код, маленькие функции. Комментарии только короткие и только там, где неочевидно. Публичное поведение объясняйте в docstring и документации.

## Документация

Любые тексты для людей (README, `docs/`, примеры, сообщения об ошибках) пишем по `docs/WRITING_DOCS.md`. Коротко:

- **Дружелюбно и просто.** На «вы», повелительное наклонение, без канцелярита.
- **Задача, потом подробности.** Сначала рабочий пример, потом пояснение. Страница читается за пару минут.
- **Заранее отвечаем на вопросы.** Что может пойти не так и что делать, пишем рядом с примером.
- **Без лишнего.** Не повторяем один факт в нескольких файлах, а ставим ссылку. История исследования уходит в конец страницы.
- **Честно о границах.** Не обещаем непроверенного, не проверили на живом ИТД, так и пишем, одной фразой.
- **Безопасно.** В примерах только вымышленные значения.

Меняете поведение SDK? Обновите страницу в `docs/` в том же PR. Переименовали заголовок? Проверьте якорные ссылки через `grep -rn`. README примера в `examples/*/` держите в 5–10 строк: это проверяет `tests/test_examples.py`.

## Секреты

Не публикуйте и не выводите в логи: токены, cookie, заголовки авторизации, файлы сессий, курсоры, личные сообщения, локальные окружения и содержимое `.bundle`. В тестах и примерах используйте только вымышленные значения. Не удаляйте локальные сессии и данные пользователя. Меняя `.gitignore` или упаковку, отдельно проверьте состав Git и архивов: игнорирование не убирает секрет из уже существующей истории.

## Проверки

Запускайте то, что соответствует изменениям:

```sh
python -m ruff check itd_bot examples tests
python -m ruff format --check itd_bot examples tests
python -m pytest -q
python -m build
```

Для упаковки добавьте `python -m twine check dist/*` и проверьте содержимое wheel и sdist и версию. Меняете API? Добавьте тесты: успешный запрос, форма ответа и ошибки, включая 401, 429 и сбой сети. Живые запросы и долгие проверки делайте только в рамках задачи и с сессией, которую дал пользователь. Честно сообщайте о том, что не прошло, и не выдавайте локальные тесты за проверку сервера.

## Git и выпуск

Основная ветка `main`; ветки, коммиты и описание PR оформляйте по `GIT_WORKFLOW.md`: заголовок в формате Conventional Commits в описательной форме, описание короткое и только по делу. Предпочтительны PR и зелёный CI, но правила GitHub настраиваются отдельно.

Без разрешения пользователя не создавайте коммиты, теги и релизы и ничего не отправляйте во внешний репозиторий. Не используйте force push и не переписывайте чужую историю. Перед добавлением файлов проверьте содержимое на секреты.

Версия лежит в `pyproject.toml`, а выпуск делает Python Semantic Release по тегам и Conventional Commits. Первый релиз без тегов явно выбирает 1.0.0. Перед выпуском проверьте предпросмотр, версию, changelog и артефакты. GitHub Release и публикация в PyPI — отдельные действия владельца и только по его явной просьбе.

## Когда закончили

Расскажите: что изменили и зачем, какие проверки прошли, что осталось неизвестным. Обновляйте примеры и документацию, если это входит в задачу, и уважайте запрет пользователя на их изменение. Не обещайте полной поддержки сервера по одним наблюдениям фронтенда.
