# Работа с ITD ChatBot SDK

Эти инструкции предназначены агентам и разработчикам репозитория. Уточнения и прямые просьбы пользователя важнее общих правил ниже. Если пользователь не программист, самостоятельно выполните доступные проверки и объясните результат простыми словами, включая ограничения и необходимые ему действия.

## Перед началом работы

1. Прочитайте этот файл, условия задачи и относящиеся к ней файлы. Сохраните существующие изменения пользователя; не перезаписывайте их и не меняйте документы, которые он попросил сохранить.
2. Для процесса разработки и чеклиста прочитайте `dev.md`; правила веток, PR и коммитов находятся в `GIT_WORKFLOW.md`, выпуск и публикация - в `RELEASING.md` и `docs/PUBLISHING.md`. `CLAUDE.md` ссылается на этот файл.
3. `README.md` и `docs/GETTING_STARTED.md` описывают установку и первого бота, `docs/USAGE.md` и `docs/API_REFERENCE.md` - интерфейс, `docs/AUTH.md` - сессию, `docs/ROUTE_INVENTORY.md` - инвентаризация API. При несоответствии проверяйте код и исходный бандл, не предполагайте, что документация или серверная спецификация безошибочны.
4. Учитывайте расположение репозитория и действующие разрешения окружения. Не создавайте новую копию или ветку без необходимости; проверяйте состояние Git до любых изменений истории.

## Устройство и границы проекта

- `itd_bot/client.py` содержит синхронный HTTP-клиент `Bot`, методы API, получение событий и передачу файлов. `auth.py` отвечает за обновление access-токена и сохранение ротируемой refresh-cookie. `dispatcher.py` маршрутизирует команды и события, `formatting.py` строит сущности форматирования, `errors.py` и `rate_limits.py` отвечают за ошибки и паузы. Сверяйте актуальную структуру с файлами, она может меняться.
- `examples/` содержит примеры, `tests/` - автономные проверки с подменой HTTP-транспорта, `.github/workflows/` - CI и релизы, `pyproject.toml` - зависимости и версия.
- SDK основан на клиентском бандле ИТД и работает от имени пользовательского аккаунта. Наблюдаемое в бандле поведение не является полной спецификацией сервера. Не выдумывайте маршруты, квоты, гарантии доставки, схему полей или идемпотентность; явно сообщайте, что не проверено.
- При изменениях сохраняйте публичную совместимость, исходные поля JSON и безопасность произвольных путей. Учитывайте обработку 401 и ротацию сессии, блокировки 429, потоковую загрузку файлов, UTF-16 в форматировании, отметку прочтения до обработчика, typing и повторную доставку событий. Курсор сохраняется только после успешной обработки пакета; `ResetRequired` нельзя скрывать.
- Не повторяйте автоматически операции записи без подтверждённой сервером идемпотентности. Ошибка сети может означать как неудачу, так и выполненную запись. Пауза после 429 не означает знания фактических квот сервера. Разные процессы не координируют локальные ограничения или refresh-сессию.
- Пишите понятный код с типами и небольшими функциями. Комментарии в коде допустимы только краткие и по делу в неочевидном месте; публичное поведение объясняйте через docstring и документацию по задаче.

## Секреты и данные

Не публикуйте токены, cookie, заголовки авторизации, файлы сессий, курсоры, личные сообщения, локальные окружения и содержимое `.bundle`. Не выводите секреты в логи или результаты проверок. Тесты и примеры используют только вымышленные значения. Не удаляйте локальные сессии и данные пользователя при уборке. Изменяя `.gitignore` или упаковку, отдельно проверяйте состав Git и архивов; игнорирование само по себе не удаляет секрет из уже существующей истории.

## Проверки

В установленном окружении проекта выполните проверки, соответствующие изменениям:

```sh
python -m ruff check itd_bot examples tests
python -m ruff format --check itd_bot examples tests
python -m pytest -q
python -m build
```

Для упаковки дополнительно проверьте wheel и sdist через `python -m twine check dist/*`, их содержимое и актуальную версию. При изменении API добавляйте значимые автономные тесты: успешный запрос, форму ответа и соответствующие ошибки, включая 401, 429 и сетевой сбой. Реальные запросы и длительные проверки выполняйте только в рамках задачи и с предоставленной пользователем сессией. Сообщайте о неработающих или непройденных проверках, не выдавайте локальные тесты за проверку сервера.

## Git и выпуск

Основная ветка - `main`; рабочие ветки и Conventional Commits описаны в `GIT_WORKFLOW.md`. Объединение через PR и проверку CI рекомендуется, но правила GitHub настраиваются отдельно. Не создавайте коммиты, теги, релизы и не отправляйте изменения во внешний репозиторий без разрешения пользователя; не используйте принудительный push или переписывание чужой истории. Перед добавлением файлов проверяйте содержимое и секреты.

Версия находится в `pyproject.toml`; выпуск делает Python Semantic Release по истории тегов. Первый выпуск без тегов в workflow явно выбирает major 1.0.0. Последующие версии определяются тегом и Conventional Commits, поэтому перед выпуском проверяйте preview, версию пакета, changelog и артефакты. GitHub Release и публикация в PyPI - отдельные действия, требующие настройки владельцем и его явного запроса.

## Завершение

Расскажите, что изменено и зачем, какие проверки прошли и что осталось неизвестным. Обновляйте примеры и документацию, когда это входит в разрешённый объём задачи; уважайте явный запрет пользователя на их изменение. Не обещайте полной поддержки сервера только по наблюдениям фронтенда.
