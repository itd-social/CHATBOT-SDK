# Git workflow

Здесь собраны правила работы с Git в этом репозитории. Если вы вносите изменения, чтобы помочь разработке (человек или агент), следуйте им.

## Ветки и pull request

1. Обновите `main` из `origin` и создайте ветку от свежего состояния: `feat/command-router`, `fix/session-refresh`, `docs/getting-started`.
2. Вносите связанные изменения и добавляйте тесты и документацию вместе с кодом. Токены, локальные сессии, архив бандла и собранные файлы в коммит не попадают.
3. Запустите проверки из [dev.md](dev.md) и откройте PR в `main`. Заголовок и описание оформите по [правилам ниже](#описание-pull-request).
4. Дождитесь зелёного CI и ревью. Объединяем через squash merge: итоговый заголовок должен быть в формате Conventional Commits.
5. После слияния удалите ветку. Релиз — отдельный шаг: [RELEASING.md](RELEASING.md).

Защита `main`, обязательные проверки и права на слияние настраиваются в GitHub, а не в репозитории.

## Описание pull request

Пишите коротко и по делу.

- **Заголовок.** Формат Conventional Commits, и по нему сразу понятно, что изменилось. Если заголовка хватает, описание можно не писать.
- **Когда нужен контекст,** в одном-двух предложениях опишите проблему и результат.
- **Для сложных изменений** добавьте только то, что поможет проверить: важные ограничения, нетривиальный способ проверки, существенные риски.
- **Чего не писать:** очевидные действия, список всех изменённых файлов и стандартные проверки «для объёма». Их результат виден в CI.
- **Если проверка не прошла или не выполнялась,** обязательно скажите об этом.

## Коммиты

Формат: `<type>(<scope>): <описание>`. Scope необязателен. Описание пишем в описательной форме, с заглавной буквы. Если причина изменения неочевидна, объясните её в теле коммита.

```text
feat(messages): Добавлена пересылка сообщений
fix(auth): Исправлена ротация cookie
docs: Добавлено больше примеров обработки команд
chore(deps): Обновлён httpx
```

Что получится в версии:

| Тип | Версия |
|---|---|
| `feat`, `feature` | minor |
| `fix`, `perf`, `refactor`, `revert` | patch |
| `!` после типа или `BREAKING CHANGE:` в теле | major (пока версия `0.x`, minor) |
| остальные (`docs`, `test`, `chore`…) | попадают в changelog, но релиз не создают |

Точный результат перед выпуском покажет dry-run: [RELEASING.md](RELEASING.md#посмотреть-план).
