# Git workflow

## Ветки и pull request

1. Обновите локальную `main` из `origin`, создайте рабочую ветку от актуального состояния: `feat/command-router`, `fix/session-refresh` или `docs/getting-started`.
2. Вносите связанные изменения и добавляйте тесты и документацию вместе с кодом. Не включайте токены, локальные сессии, архив бандла или собранные файлы.
3. Запустите проверки из [dev.md](dev.md) и откройте pull request в `main`. В описании укажите проблему, итоговое поведение, проверки и ограничения.
4. Дождитесь успешного CI и проверки изменений. Рекомендуемый способ объединения — squash merge; итоговый заголовок должен соответствовать Conventional Commits.
5. После объединения удалите рабочую ветку. Релиз — отдельный шаг по [RELEASING.md](RELEASING.md).

Правила защиты `main`, обязательные проверки и права на объединение настраиваются в GitHub: один файл в репозитории их не включает.

## Коммиты

Формат: `<type>(<scope>): <описание>`. Scope необязателен. Используйте повелительную или описательную форму и объясняйте причину в теле, если она неочевидна.

```text
feat(messages): добавить пересылку сообщений
fix(auth): сохранить ротированную cookie
docs: добавить пример обработки команд
chore(deps): обновить httpx
```

`feat` и `feature` повышают minor, `fix`, `perf`, `refactor` и `revert` — patch; `!` после типа или `BREAKING CHANGE:` в теле обозначает несовместимое изменение. Пока версия `0.x`, настроен переход на следующий minor для breaking change. Остальные типы могут попасть в changelog, но не обязательно создают новый релиз. Точный результат перед выпуском показывает dry-run.
