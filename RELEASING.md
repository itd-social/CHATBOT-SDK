# Релизный процесс ITD ChatBot SDK

Версия хранится в `pyproject.toml`. Для Python-проекта используется [Python Semantic Release](https://python-semantic-release.readthedocs.io/) — аналог release-it, который вычисляет версию из Conventional Commits, обновляет `CHANGELOG.md`, создаёт коммит и тег, собирает пакет и создаёт GitHub Release. Настройки находятся в `pyproject.toml`.

## До релиза

- Рабочая ветка `main`, актуальный `origin/main`, нет незакоммиченных изменений.
- Изменения прошли PR и CI; [чеклист разработки](dev.md#чеклист-изменения-sdk) выполнен.
- В Git нет refresh-токенов, файлов сессий, личных сообщений и бандла.
- Репозиторий имеет доступный remote `origin`, полную историю и теги. GitHub Actions должна иметь право создавать релизы и отправлять коммиты и теги; правила защиты `main` могут запрещать прямой push для `GITHUB_TOKEN`.
- Версия пакета в `pyproject.toml` и история тегов согласованы. Это особенно важно перед первым релизом: инструмент определяет предыдущую версию по тегам, а не только по полю `project.version`.

Установите инструменты и проверьте проект:

```sh
python -m pip install -e ".[dev,release]"
python -m ruff check itd_bot examples tests
python -m ruff format --check itd_bot examples tests
python -m pytest -q
python -m build
```

## Просмотр

```sh
semantic-release --noop version
```

Команда показывает план без изменения файлов, коммитов, тегов и удалённого репозитория. Она требует Git-репозиторий и его историю. Проверьте итоговую версию, список изменений и данные будущего релиза. В Windows для корректной обработки русских текстов перед локальными командами релиза задайте `$env:PYTHONUTF8 = "1"` в PowerShell или `set PYTHONUTF8=1` в cmd.

В GitHub можно запустить workflow **Release** вручную на `main`. При `publish=false` (значение по умолчанию) он только запускает проверки и dry-run. При `publish=true` он создаёт релиз: workflow выполняется с `contents: write`, создаёт коммит `chore(release): vX.Y.Z`, тег `vX.Y.Z`, отправляет их в `origin/main`, создаёт GitHub Release и прикрепляет wheel и sdist. Автоматического выпуска при каждом push нет.

Если защита ветки не позволяет `GITHUB_TOKEN` отправить релизный коммит, настройте разрешённый для проекта способ выпуска или выполняйте согласованный релизный процесс с нужными правами. Не отключайте защиту ради обхода ошибки.

## Версионирование и changelog

- `feat` и `feature` - minor; `fix`, `perf`, `refactor` и `revert` - patch. Используйте формат `revert: ...`: стандартное сообщение `Revert ...` само по себе не является Conventional Commit.
- `!` или `BREAKING CHANGE:` - несовместимое изменение. До `1.0.0` настройка `major_on_zero = false` переводит его на следующий minor.
- Changelog создаётся на основе коммитов после предыдущего тега. Маркер `<!-- version list -->` в `CHANGELOG.md` нужен инструменту для вставки новых версий.
- Вид `CHANGELOG.md` и заметок GitHub Release задают шаблоны в `templates/` (`template_dir` в `pyproject.toml`): разделы со смайликами в фиксированном порядке, заголовок версии со ссылкой на сравнение тегов и строки вида `* **scope:** тема ([#5](ссылка), [abcdef0](ссылка))`. Внутри раздела строки сортируются по теме, затем по scope. Формат повторяет changelog [max-ui](https://github.com/max-messenger/max-ui) (release-it), смайлики и порядок разделов оттуда.

| Тип коммита | Раздел | Версия |
|---|---|---|
| `feat` / `feature` | ✨ Новые возможности | minor |
| `fix` | 🐛 Исправления | patch |
| `perf` | ⚡️ Производительность | patch |
| `refactor` | ♻️ Рефакторинг | patch |
| `revert` | ⏪️ Откаты изменений | patch |
| `docs` | 📚 Документация | — |
| `style` | 💎 Стили | — |
| `test` | ✅ Тесты | — |
| `chore` | 🛠 Прочее | — |
| `build` | 📦 Сборка | — |
| `ci` | 👷 CI | — |
| `!` или `BREAKING CHANGE:` | ⚠️ Несовместимые изменения | major (до `1.0.0` — minor) |

Секции без коммитов не выводятся. Коммит без распознаваемого типа в changelog не попадает. Заголовок версии и ссылки зависят от тегов `vX.Y.Z` и URL `origin`, поэтому перед выпуском проверьте результат командой `semantic-release --noop version` и после выпуска — заметки созданного GitHub Release.

## После выпуска

Проверьте GitHub Release, тег, номера версий и оба файла из `dist/`. При ошибке не переписывайте опубликованный тег и не используйте принудительный push: согласуйте исправляющий релиз с командой.

## Публикация в PyPI

PyPI не вызывается автоматически после GitHub Release. Для отдельного выпуска предусмотрен ручной workflow **Publish to PyPI**. Перед первым запуском:

1. Подтвердите, что имя `itd-chatbot-sdk` доступно в PyPI и закреплено за вашим аккаунтом. Лицензия проекта - BSL-1.0.
2. Настройте в PyPI Trusted Publisher для этого GitHub-репозитория: workflow `publish-pypi.yml`, environment `pypi`. При необходимости задайте в GitHub для environment `pypi` обязательное подтверждение владельца.
3. Создайте обычный опубликованный GitHub Release с тегом вида `v0.1.0`. Версия в теге должна совпадать с `project.version` в этом коммите.
4. Запустите **Publish to PyPI** вручную, указав тег. Workflow проверяет опубликованный GitHub Release и совпадение версии, запускает тесты, собирает пакет, выполняет `twine check` и публикует через OIDC. Только стабильные теги `vX.Y.Z` поддерживаются этим workflow.

Права доступа к PyPI и настройки Trusted Publisher в данном репозитории не создаются. До их настройки публикация завершится ошибкой. Пакет, выпущенный в PyPI, нельзя считать удаляемым или заменяемым; при ошибке подготовьте исправляющую версию.

Пошаговая инструкция с точными параметрами репозитория: [Публикация в PyPI](docs/PUBLISHING.md).
